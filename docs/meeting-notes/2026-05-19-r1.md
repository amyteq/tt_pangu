## Decisions made

### 1. LiteLLM as unified LLM provider layer

**Decision:** Introduce `litellm` as the single interface to all LLM providers.
Replace the `anthropic` direct import in `AgentWorker` with `litellm.completion()`.

Rationale: avoid lock-in to Anthropic. Kaggle competition work benefits from switching
between Claude, GPT-4o, local vLLM/Ollama depending on task type and cost.

ADR: `docs/adr/0004-litellm-provider-layer.md`

Implementation note for M3-T003/T004: `TOOL_SCHEMAS` must be in OpenAI tool schema format
(LiteLLM standard). The `model` field in `JobPolicy` becomes the litellm model string,
e.g. `"claude-sonnet-4-6"`, `"gpt-4o"`, `"ollama/qwen2.5"`.

### 2. Job taxonomy and terminology

**Decision:** The terms project, competition, session, job, experiment, run, submission are
formally defined and documented. This is product knowledge that should live in `docs/adr/`
and be readable by all AI tools working on this repo.

ADR: `docs/adr/0005-job-taxonomy.md`

### 3. Configurable approval gates — default allow

**Decision:** Human approval gates for Kaggle submit, kernel push, and git push are
**configurable per project/competition**, with the **default set to allow (no approval required)**.

Previous default (always require approval) is reversed.

Rationale: the user's Kaggle workflow is iterative and fast. The main human intervention
points are **major direction decisions** (switch model, switch approach, ensemble strategy),
not routine submission mechanics.

Specific defaults:
- `kaggle_submit`: `requires_approval: false` (default)
- `kernel_push`: `requires_approval: false` (default)
- `git_push`: `requires_approval: false` (default)
- `dataset_upload`: `requires_approval: true` (default — less common, more destructive)

ADR: `docs/adr/0006-configurable-approval-gates.md`

### 4. Budget defaults — raise significantly

**Decision:** Default budget limits are raised, especially for research-type jobs.

Updated defaults in `JobPolicy`:
| Parameter | Old default | New default |
|---|---|---|
| max_turns | 30 | 60 |
| max_cost_usd | 5.0 | 20.0 |
| max_runtime_s | 3600 | 7200 |

Research jobs specifically: max_turns=100, max_cost_usd=10.0 (divergent, exploratory).

### 5. LLM sampling parameters per job type

**Decision:** Each job type has its own recommended `temperature`, `top_p`, and optionally
`min_p`. These are stored in job policy and passed to litellm.

| job_type | temperature | top_p | reasoning |
|---|---|---|---|
| research | 0.8 | 0.95 | creative, divergent thinking |
| implement | 0.2 | 0.9 | precise, deterministic code |
| experiment | 0.1 | 0.9 | reproducible, no surprises |
| debug | 0.3 | 0.9 | careful analysis |
| eval | 0.5 | 0.9 | analytical with some exploration |
| prepare_submission | 0.1 | 0.9 | very careful, low variance |

ADR: `docs/adr/0004-litellm-provider-layer.md` (sampling params section)

### 6. Prompt language

**Decision:** Agent job prompts (the `prompt` field in `agent_jobs`) are written in English.
Chinese-language versions may be kept as comments or reference in task spec files.
LLM call parameters (temperature, top_p, min_p, model) are recorded in the job record.

### 7. Observability — OTEL/telemetry strategy

**Decision:** Introduce OpenTelemetry (OTEL) instrumentation as a future M2.5/M3 add-on for
end-to-end visibility: traces per job, spans per tool call, metrics per turn.

This enables:
- Identifying slow tools (e.g., kaggle watch polling)
- Tracking cost per job type over time
- Performance regression detection as platform evolves
- Future: compare model performance across providers (Claude vs GPT-4o vs local)

ADR: `docs/adr/0007-otel-telemetry-strategy.md`

Not blocking M3. Can be added incrementally starting with M3 or M4.

### 8. Regression test competitions — selected

**Decision:** Four Kaggle competitions are selected as the platform's regression test suite,
covering different task types, data formats, and complexity levels.

| Competition | Type | Level | Key characteristics |
|---|---|---|---|
| Titanic | Binary classification | L1 (fast, simple) | Tabular, CSV, no GPU needed |
| House Prices | Regression | L1 (fast) | Tabular, feature engineering heavy |
| Digit Recognizer | Image classification | L2 (medium) | MNIST, simple CNN, no TPU |
| Flower Classification with TPUs | Image classification | L3 (complex) | TFRecord, TPU, 104 classes |

Updated in: `docs/testing/competition-test-cases.md`
Referenced in: `docs/milestones/README.md` M10 section

## Reference: user's Kaggle competition workflow

From `docs/meeting-notes/2026-05-17-r1.md`:

1. **prep**: join competition, read rules, requirements, data
2. **initial research**: browse hot Code/Model/Discussion topics
3. **first try**: prepare code (notebook or script, own or adapted)
4. **iterate**: experiment → test → submit → evaluate → research → modify → repeat
5. **local GPU** (RTX 3090/4090): used when GPU requirements are modest
6. **submit to Kaggle** when local baseline improves; multiple candidates spread across days
7. **analysis**: compare public LB score vs CV; determine next direction
   (expand test data, tune params, switch model/library, ensemble)
