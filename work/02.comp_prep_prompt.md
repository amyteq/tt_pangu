# Task: Organize active Kaggle competition tracking
Organize active Kaggle competition tracking under `competitions/` until the documentation structure is created, existing competition notes are consolidated, and acceptance criteria are met; or stop and summarize blockers.

Mission:
Create a clean `competitions/` workspace for tracking every active or recent Kaggle competition in this repository. This task is documentation/workspace organization only. Do not promote KCA skills, do not modify KCA core, and do not perform Kaggle submissions or remote side effects.

Source of truth:
Read first:
- CLAUDE.md
- README.md
- PROJECT_STATE.md if present
- docs/milestones/README.md
- existing `competitions/` if present
- existing `experiments/` if present
- `work/` notes related to Kaggle competitions if present
- `worklogs/` entries related to Kaggle competitions if present
- `docs/tasks/` entries related to active competitions if present

Optional read-only GitHub context:
- If `gh` is available and authenticated, you may inspect relevant issue titles/comments only when they are clearly related to active competitions such as nemo or orbit.
- Do not create, edit, label, close, or comment on GitHub issues in this task unless explicitly asked later.
- If GitHub issue content is unavailable, continue with repo files and mark missing issue context as a blocker or uncertainty.

Scope:
Allowed to create or edit:
- competitions/
- competitions/README.md
- competitions/_templates/
- competitions/_shared/
- competitions/<competition>/
- docs/tasks/ only if you need to create a small follow-up task proposal
- README.md only if a short pointer to competitions/ is necessary

Allowed to move with `git mv` only if the mapping is obvious:
- root-level `experiments/<competition-like-name>/` → `competitions/<competition>/...` or `experiments/<competition-like-name>/` → `competitions/<competition>/experiments/...`

Do not move files if ownership is ambiguous. Instead, document the proposed move in:
- competitions/_shared/migration-notes.md

Non-goals:
- Do not modify `.kca/skills/`.
- Do not modify `tools/kca/`.
- Do not modify `src/`, `services/`, `supabase/`, `ui/`, `.github/workflows/`, migrations, CI, or permission policy.
- Do not implement new competition code, notebooks, models, agents, or experiments.
- Do not run training, long notebooks, Kaggle kernels, or Kaggle submissions.
- Do not create KCA common skills yet.
- Do not over-document; keep summaries compact and link to source evidence.

Forbidden paths and actions:
- Do not read `.env`, `.env.*`, `kaggle.json`, `.kaggle/kaggle.json`, `secrets/**`, SSH keys, AWS/GCP credentials, or any credential file.
- Do not run `kaggle competitions submit`, `kaggle kernels push`, `kaggle datasets create`, or any equivalent wrapper command.
- Do not run destructive commands.
- Do not force-push.
- Do not merge PRs.
- Do not delete source notes, issues, worklogs, or old docs. Preserve or link them.

Competition classification rules:
- A `competition` is an external Kaggle competition/challenge with a slug, rules, metric, data, leaderboard, deadline, or submission channel.
- An `experiment` is a hypothesis, model route, notebook version, feature set, agent version, or submission attempt under a competition.
- If `nemo` is a real Kaggle competition, create `competitions/nemo/`.
- If `nemo` is only a method/model/experiment for another competition, place it under `competitions/<parent-competition>/experiments/nemo-*` and explain the decision.
- Existing `orbit-wars` should be treated as a competition if it corresponds to Orbit Wars or another external competition. `orbit` is an alias to `orbit-wars`
- Root-level `experiments/` should remain only for KCA platform experiments, not real Kaggle competition work.
- When moving `experiments/nvidia-nemotron-model-reasoning-challenge` to `competition/`, shorten `nvidia-nemotron-model-reasoning-challenge` as `nvidia-nemotron`, aliases are `nemo`, `nemotron`
- If unsure whether something is a competition or experiment, do not move it; create a clear note in migration-notes.md with evidence and a proposed decision.

Migration / consolidation process:
1. Inventory existing sources.
2. Identify all competition-like folders and notes.
3. Build or update `competitions/` structure.
4. Move files only when mapping is obvious.
5. For each active competition, create/update the required docs.
6. Update `competitions/README.md` dashboard.
7. Record ambiguous moves in `competitions/_shared/migration-notes.md`.
8. Summarize the final diff and remaining blockers.

Content rules:
- Use Chinese for human-facing explanations.
- Keep code paths, file names, commands, labels, metrics, Kaggle slugs, config keys, notebook names, and variable names in English.
- Do not translate machine-readable labels or file names.
- Do not turn README files into long tracking issues.
- Preserve evidence links to original notes/worklogs/issues.
- Mark uncertainty explicitly.
- Prefer short current-state summaries plus links to detailed files.
- Do not duplicate large issue/comment/worklog content verbatim.
- Do not make claims about scores, submissions, or rules unless evidence exists.

Validation required:
Run lightweight checks only:
- `git status --short`
- `find competitions -maxdepth 3 -type f | sort`
- If available, run a simple markdown sanity check already used by the repo.
- Do not run full training, notebooks, Kaggle commands, or long tests.
- If you modify only Markdown/YAML docs, full pytest is not required; state that tests were not run because this is docs-only.
- If you add any script or code unexpectedly, stop and ask for scope confirmation instead.

- `competitions/README.md` exists and has an active competitions dashboard.
- `competitions/_templates/` exists with reusable templates.
- `competitions/_shared/` exists with README, insights, common-bugs, skill-candidates, and migration-notes.
- Each clearly identified active competition has:
  - `competition.yaml`
  - `README.md`
  - `rules.md`

  - `submissions.md`

- Existing root-level competition material is either moved safely or documented as an unresolved migration note.
- `experiements/` typo is corrected only if safe; otherwise documented.
- No KCA core files are changed.
- No `.kca/skills/` files are changed.
- No secrets are read.
- No remote side effects are performed.
- Final response includes:
  - files created
  - files modified
  - files moved
  - ambiguous items
  - tests/checks run
  - proposed follow-up issues
  - risks and next steps

Stop conditions:
Stop immediately and summarize blockers if:
- source context is too ambiguous to classify safely;
- a secret/credential path is encountered;
- the task requires Kaggle submit/kernel push/dataset upload;
- the task requires editing `.kca/skills/`, `tools/kca/`, `src/`, `supabase/`, `.github/workflows/`, or CI;
- moving files would risk data loss or unclear ownership;
- scope expands beyond documentation/workspace organization;
- acceptance criteria are met.
