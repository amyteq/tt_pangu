hidden_constraints:
  1. The Devpost rules page for `h01` (docs/evidence/m12/t000-candidates.md:88–101) does not enumerate a rate-limit on form-submit POSTs — what does M12 assume about Devpost rate-limit semantics, and what happens if T007's submit POST is silently throttled / queued? — consequence if unanswered: the reviewer-gate fires, the human approves, the submit POST returns 200 but the form is queued by Devpost and never reaches the leaderboard; we record a fake-success `submissions` row.
  2. The `h01` event requires AWS-credit registration via a Google form by Jun 26 12pm PT (docs/evidence/m12/t000-candidates.md:115–116) — does ADR-0018 need a "pre-submission registration deadline" field on `competitions` (separate from `deadline timestamptz`)? — consequence if unanswered: M12-T006 assembles a submission_pack and T007 submits, but the AWS-credit deadline silently passes; the run looks valid but the entry is ineligible for the cash prize.
  3. The `h01` event's "Functionality" judging gate ("must be capable of being successfully installed and running consistently"; docs/evidence/m12/t000-candidates.md:108–112) implies the submission pack must include reproducible install instructions — does `submission_checklist` (M12-T004) need a "reproducibility" axis distinct from "completeness"? — consequence if unanswered: T007 submits a pack that the checklist marks "complete" but a Devpost judge cannot install; we pollute a managed-by-Devpost event.
  4. Devpost is a managed third-party SaaS — does the policy gate on `devpost_submit` need to record the Devpost session-cookie / API-token shape (T003 / T007 pick) as a key on `competition_policy`, so a key rotation invalidates outstanding gate approvals? — consequence if unanswered: a human approves a `devpost_submit` decision, the credential rotates between approval and execution, T007 silently submits under a different identity (or fails with auth that doesn't roll back the approval row).
  5. ADR-0006 (docs/adr/0006-configurable-approval-gates.md:30–43) declares `kaggle_submit: false` (default-allow) but the per-competition `competitions.competition_policy` (supabase/migrations/0004_m4_competition_repo.sql:18) can flip it — does the `devpost_submit` gate default to `ask` (M12 default per docs/milestones/m12/loop-prompts.md:298) or `allow` to match ADR-0006 default-allow philosophy? — consequence if unanswered: a future hackathon row inherits `default-allow` and a worker accidentally submits the first prototype.
  6. The `competition-runner.yaml` profile gates `supabase_migrate: ask` (.kca/permissions/competition-runner.yaml:15) but does NOT enumerate `devpost_submit` — what is the fallback decision for an unknown op on a profile that does enumerate other ops? — consequence if unanswered: the resolver (tools/kca/agent/permission_policy.py:50–51) falls back to `_tool_default_decision(operation)` which returns `"ask"` for unknowns; but ADR-0018 should make this explicit so a future Devpost-runner profile inherits the default rather than silently allowing.

personas_and_accounts:
  1. The `h01` event allows solo / team / organization entries (docs/evidence/m12/t000-candidates.md:73–74); ADR-0018 must decide whether `competition_type='devpost'` rows can carry a NULL `team_id` (solo entry) or whether every Devpost row must reference a team — consequence if unanswered: M12-T002 schema either over-constrains (forces a `team_id` for solo entries) or under-constrains (silently allows two solo entries that should have been a team).
  2. The task spec says "M12 ships read-only team membership only" (docs/tasks/m12/M12-T001-discovery-debate-gate.md:91–92) and "all gates default to `owner-only` for now" (docs/tasks/m12/M12-T001-discovery-debate-gate.md:90) — who is the "owner" when the team has multiple members and the row was inserted by the agent? — consequence if unanswered: an approval gate fires, two team members both have approval power, both approve, the audit log records two `human_decisions` rows with `status='approved'` for one job; what does T007 do?
  3. The Devpost session-cookie / API-token auth shape is "TBD per T003" (docs/milestones/m12/loop-prompts.md:386–391) — does ADR-0018 commit to a single auth-shape (env-var only, no per-row override) or anticipate a multi-Devpost-account future (the legacy kkr.py multi-account pattern, tools/legacy/kkr.py:541)? — consequence if unanswered: if a second Devpost account is added in M12.x, the schema either accommodates it cleanly or requires a second migration; the canonical failure mode the Discovery / Debate Gate exists to prevent (docs/architecture/discovery-debate-gate.md:18–22).
  4. Existing Kaggle rows have an implicit "owner = whoever set KAGGLE_USERNAME in process env" persona (legacy archaeologist §3); ADR-0018 does not name a "row owner" column today — does the team-scoped rule need a `competitions.created_by_user_id` column (M12-T002) to disambiguate "the human who registered the row" from "the team that owns the submission"? — consequence if unanswered: when team A registers the competition and team B's member triggers the gate, the audit log cannot reconstruct who is the "owner" for the owner-only default.
  5. The Devpost "team" model (Devpost has its own team / collaborator concept on each event page) is not the same as the M12 `teams` table — does ADR-0018 commit to "M12 team = a local-only KCA team, no Devpost-side team sync" or anticipate sync? — consequence if unanswered: the human approves a `devpost_submit` thinking the submission credits the M12 team, but Devpost records only the submitting account; team credit is lost.
  6. The `kca decisions approve --id <id>` CLI (docs/adr/0006-configurable-approval-gates.md:113–115) has no notion of "who is approving" — does ADR-0018 add a `human_decisions.approved_by_user_id` column or accept that the owner-only rule is enforced by social convention only? — consequence if unanswered: the team-scoped rule is documentation-only and the audit log cannot prove who approved a `devpost_submit`.

side_effects:
  1. The single M12 real Devpost submission (M12-T007 scope) writes a permanent, publicly-visible entry on a managed-by-Devpost event (docs/evidence/m12/t000-candidates.md:34, "managed by Devpost") — what reverses it? Devpost generally allows "withdrawing" a submission via the event page; ADR-0018 should record whether `devpost_withdraw` is a known operation and whether it is gated. — consequence if unanswered: a rejected / spammy submission cannot be removed without manual human action; the audit log has no `withdrawn_at` column to record the reversal.
  2. The `competitions` table receives a new row on `kca devpost register` (M12-T003 scope) — does ADR-0018 require `register` to be idempotent (re-running on the same slug must not insert a duplicate, must update the existing row)? — consequence if unanswered: T003 retries cause duplicate rows; the smoke tests in M12-T008 assert "row exists" but cannot assert "exactly one row".
  3. The READ_ONLY Devpost page-fetch (M12-T003) hits a public URL via the research-fetch HTTP path (docs/milestones/m12/loop-prompts.md:259) — does it require a sandbox bypass (devpost.com is not in the allowed-hosts list per memory `reference_sandbox_network.md`)? — consequence if unanswered: T003 fails inside the sandbox; the operator must `dangerouslyDisableSandbox=true` for every fetch without ADR-0018 documenting why.
  4. The reviewer-gate writes `agent_reviews` + `human_decisions` rows (docs/milestones/m12/loop-prompts.md:540–550) and on approval transitions to a real submit — what reverses the audit-log claim "human approved" if the human reconsiders between approval and the submit fire? — consequence if unanswered: there is a race window where `human_decisions.status='approved'` is true but the submit POST has not yet fired; if the human revokes via DB UPDATE, the worker still proceeds.
  5. Net-new for `team_invite=deny` (docs/milestones/m12/loop-prompts.md:298) — what fires if a skill calls `team_invite` and the resolver returns `deny`? Does the worker exit, prompt for permission, or silently no-op? — consequence if unanswered: a skill author writes a `team_invite` call thinking it will ask, the resolver denies, the agent loop crashes / loops.
  6. `competition_policy` jsonb on a `competition_type='ctf'` row is reserved for M11 (docs/tasks/m12/M12-T001-discovery-debate-gate.md:81–83) but the M12 migration ships the enum value — what stops an M12.x experiment from inserting a `ctf` row and triggering an undefined permission profile? — consequence if unanswered: an out-of-band CTF experiment lands a row whose `competition_type='ctf'` resolves to the `default` profile and the `ctf_*` operations behave as `ask` (acceptable) or `allow` (bad).

edge_cases:
  1. A `competition_type='devpost'` row with `submission_format jsonb = NULL` — what does the `submission_checklist` tool emit? — consequence if unanswered: M12-T004's checklist tool either crashes (KeyError) or emits an empty checklist that the agent treats as "done", short-circuiting the gate.
  2. A `competition_type='kaggle'` row whose `competition_policy` carries `devpost_submit: allow` (legacy-archaeologist §8) — does the resolver honour it, ignore it, or reject the row at insert time? — consequence if unanswered: a stale/copy-pasted Kaggle row silently enables Devpost submit; foot-gun.
  3. The `deadline timestamptz` column is `NULL`-able (docs/milestones/m12/loop-prompts.md:233) — what does the UI countdown render for `NULL`? — consequence if unanswered: HackathonDeadline.tsx (M12-T005) crashes on `null` or renders "NaN".
  4. Two rows with the same Devpost slug but different `competition_type` ('devpost' vs 'hackathon_devpost') — ADR-0018 must say whether `(slug, competition_type)` is the uniqueness key or `slug` alone is. — consequence if unanswered: T003 register can collide with a future re-categorisation; the migration should record this.
  5. Team_memberships UNIQUE(team_id, user_id) but no constraint on "every team has ≥1 member" — what happens to a team row whose only membership row is deleted? — consequence if unanswered: orphan team rows accumulate; the team-scoped owner-only rule has no "owner" to fall back to.
  6. The kaggle-experiment-loop skill's submission-gate prose (.claude/skills/kaggle-experiment-loop/SKILL.md:39–42) is Kaggle-specific — what happens if a Devpost competition_type runs the kaggle-experiment-loop skill by mistake (wrong skill bound)? — consequence if unanswered: the agent submits a CSV to a Devpost endpoint; the resolver allows `kaggle_submit` because the bound profile is the wrong one.

rollback:
  1. ADR-0018 + Migration 0008 add a `competition_type_enum` Postgres TYPE — what is the rollback if the migration is reverted after rows reference the enum? — consequence if unanswered: the column drop must precede the type drop; if either Spaceship-Titanic or TPU rows backfilled to `'kaggle'` cannot be re-cast, the rollback fails.
  2. ADR-0018 commits to backfilling existing rows to `competition_type='kaggle'` (docs/tasks/m12/M12-T001-discovery-debate-gate.md:94–97) — what proves the backfill is correct? — consequence if unanswered: the M9 / M10 baseline rows backfill silently; if even one row backfills wrong, the policy resolver routes the wrong gates and we cannot tell from logs alone.
  3. The `teams` + `team_memberships` tables are net-new (M12-T002) — what reverses a `teams` row insert? — consequence if unanswered: minimal team model has no delete path in M12 (per docs/milestones/m12/loop-prompts.md scope "no delete in M12"); test rows accumulate and pollute the local DB.
  4. The `hackathon-runner.yaml` profile is net-new (M12-T004); a bug in the profile (e.g. `devpost_submit: allow` instead of `ask`) is a single-file fix BUT the file is loaded fresh on every resolver call (tools/kca/agent/permission_policy.py:79–88). What proves a profile change rolls back cleanly mid-run? — consequence if unanswered: a mid-run profile edit changes the gate decision for in-flight gates; idempotency unclear.
  5. If the M12-T007 real submit succeeds and writes a `submissions` row but the Devpost-side entry is later rejected by a judge (post-deadline review), what marks the local row "rejected"? — consequence if unanswered: the audit log says `status='submitted'` forever; no follow-up flow to reconcile.
  6. If ADR-0018 supersedes ADR-0006 by accident (the task says "supersede neither"; docs/tasks/m12/M12-T001-discovery-debate-gate.md:93), reverting the supersession requires editing the ADR header — what catches a wrong "Supersedes:" line in CI? — consequence if unanswered: a future reader treats ADR-0006 as retired and the four-level hierarchy is silently lost.

explicit_unknowns:
  - The Devpost session-cookie / API-token auth shape that M12-T003 will pick (cookie-jar reuse from a browser session, hand-issued API token, or a third option). ADR-0018 must either commit to a single shape now or explicitly leave it to T003 with a follow-up to amend ADR-0018 once the shape is picked.
  - Whether the `competition_type` column should be `NOT NULL DEFAULT 'kaggle'` (no NULL rows ever) or `NOT NULL DEFAULT 'kaggle'` after a backfill UPDATE (allow brief NULL during backfill). The migration shape (docs/milestones/m12/loop-prompts.md:232–233) suggests the former, but the M9 / M10 row count needs human confirmation that the backfill UPDATE runs in <1s.
  - The exact set of new approval ops to add to the resolver (`devpost_submit`, `demo_upload`, `team_invite` — docs/milestones/m12/loop-prompts.md:298–300) vs. ops that are out of scope (`devpost_withdraw`, `devpost_edit`, `team_invite_revoke`).
  - Whether `competition_type='hackathon_devpost'` (M12 ships both per docs/tasks/m12/M12-T001-discovery-debate-gate.md:81) is reserved for Devpost-hosted *hackathon* events specifically, or any hackathon hosted anywhere (HackerEarth, Devfolio) with the Devpost form-shape. ADR-0018 must define the boundary.
  - Whether the M11 `ctf` reuse means M11 will add a `ctf-runner.yaml` profile (parallel to `hackathon-runner.yaml`) or extend `competition-runner.yaml`. The schema shape allows both; ADR-0018 should name the expectation so M11 doesn't re-debate.
  - Whether the team-scoped rule (which ops a non-owner can trigger) needs a `JobPolicy.team_role: 'owner'|'member'` field today or can be deferred to a M12.x follow-up.
