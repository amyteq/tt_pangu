# Q1:
接着之前问的关于 skills, tools, agent, MCP 的问题：
- skills 之间是否能互相调用？
- tools 一般是否需要注册到agent 中，这样 agent 和 skills 知道有哪些tools 以及如何调用？ 
- tools 如何注册到 agent 中？
- agent 是不是相当于一个平台，用来根据外部输入，来动态调用 多个 skills 来完成任务？
- 那么当外部输入不变的时候，skills 的调用顺序和具体调用是否有可能不总是一样？
- skill 是不是也有这样的不确定性？
- 那么如何确保 agent 和 skill 的稳定输出？是不是就要通过 harness engineering 来加强？

# A1:
可以把这几个概念这样分层理解：

```text
Agent = 决策循环 / 编排器
Skill = 可被 agent 加载的工作流说明书 / recipe
Tool = 可执行动作 / function / command / API
MCP = 一种把外部 tools/data sources 接到 agent 的协议
Harness = 围绕 LLM 的确定性工程层：状态机、队列、权限、测试、审计、重试、验证、预算
```

对你的 KCA 平台来说，**不要把稳定性寄托在“模型会不会按某个 skill 顺序自然行动”上**。应该让 KCA 自己的 harness 决定：可用哪些 skills、可用哪些 tools、按什么状态机推进、什么时候暂停等待 decision、什么时候重试、什么时候失败。

---

## 1. Skills 之间是否能互相调用？

**在 Claude Code 原生语义里，skill 不是严格意义上的函数，所以不要把“skill A 调用 skill B”理解成确定性的函数调用。**

Claude Code 的官方说法是：skill 是 `SKILL.md` 文件；Claude 会在相关时使用它，或者用户可以直接输入 `/skill-name` 调用它；custom commands 现在也并入 skills，`.claude/commands/deploy.md` 和 `.claude/skills/deploy/SKILL.md` 都可以创建 `/deploy`。([Claude API Docs][1])

所以有三种情况：

```text
A. 用户直接调用：
   /run-milestone M9-T002

   这是最稳定的。

B. Claude 自动调用：
   用户说“帮我总结日志”，Claude 根据 skill description 自动加载 triage-log。

   这是模型决策，不保证每次完全一样。

C. 一个 skill 的说明里写：
   “完成后使用 review-pr skill 复核。”

   这属于模型遵循说明，不是硬调用链。
```

Claude Code 确实支持复杂 skill、supporting files、动态 shell context、以及 `context: fork` 让某个 skill 在隔离 subagent context 中运行；官方文档说 `context: fork` 会把 skill 内容作为 subagent prompt，结果再汇总回主对话。([Claude API Docs][1]) 这可以做“组合”，但仍然不是传统程序里的 function call graph。

**对 KCA 的建议：**

```text
不要依赖 skill A 自然触发 skill B。
要么：
  1. 建一个 orchestrator skill，例如 run-milestone；
  2. 要么在 KCA Job Runner 里显式定义 skill pipeline / DAG；
  3. 要么把多个步骤写成一个状态机：plan → implement → test → review → decision → closeout。
```

KCA M7 已经把 Command / Skill / Tool / Job 定义成四层：Command 是确定性 CLI/API 入口，Skill 是 agent-facing workflow recipe，Tool 是带 schema/timeout/permission/audit 的可执行动作，Job 是带预算、turn、runtime、decision gates 的 durable run。 这正是你应该采用的抽象。

## 2. Tools 一般是否需要注册到 agent 中？

**是的。agent 必须知道有哪些 tools、每个 tool 做什么、输入 schema 是什么、权限/副作用是什么，才能可靠调用。**

在 Claude Agent SDK 里，自定义 tool 是带 name、description、input schema、handler 的函数；官方文档说 tool 的 description 会被 Claude 用来判断何时调用，input schema 定义参数，handler 执行实际动作。定义后要 wrap 到 SDK MCP server，然后传给 `query()` 的 `mcpServers`。([Claude Code][2])

在 Claude Code/MCP 里，MCP server 连接后会把 tools 暴露给 Claude；Claude Code 也支持 `claude mcp add ...` 添加 HTTP/SSE/stdio/WebSocket MCP server，并可用 `/mcp` 查看连接状态。([Claude Code][3])

所以 KCA 中应该有一个明确的 Tool Registry，例如：

```yaml
# .kca/tools/tools.yaml
tools:
  kca.run_tests:
    description: Run project tests in current workspace.
    input_schema:
      test_selector: string
    side_effect: local-read
    timeout_s: 300
    permission: allow
    sandbox: workspace
    idempotent: true

  kca.kaggle_submit:
    description: Submit prepared file to Kaggle competition.
    input_schema:
      competition: string
      submission_file: string
      message: string
    side_effect: remote-submission
    timeout_s: 600
    permission: ask
    sandbox: external
    idempotent: false
```

然后 agent 看到的不是随意 bash 命令，而是稳定 tool surface：

```text
kca.run_tests
kca.prepare_submission
kca.record_metric
kca.triage_log
kca.kaggle_submit
kca.create_pr
```

M7 的权限设计也已经写明：runtime permissions 应该是数据，不是 ad-hoc prompts；默认允许 workspace edits、测试、benchmark、artifact、log summary、LiteLLM/local models、branch/commit/PR；decision gate 包括 Kaggle submit、merge PR、publish dataset/kernel、remote Supabase migration、spend above budget、change model tier、change direction/objective；deny 包括 secrets、workspace 外写入、sudo/root、drop database、force push、network exfiltration。

## 3. Tools 如何注册到 agent 中？

要看你说的是 Claude Code、Claude Agent SDK，还是 KCA 自己的平台。

### Claude Code CLI

常见来源有：

```text
1. Built-in tools
   Read, Write, Edit, Bash, Grep, Glob 等。

2. MCP tools
   claude mcp add ...
   或项目级 .mcp.json。

3. Project/user/plugin skills 中的 allowed-tools / disallowed-tools。
   这不是注册 tool 本身，而是给 skill 运行时预批准或限制 tool 使用。

4. Subagent definition 中的 tools 字段。
```

Claude Code 的 MCP 文档说明 project-scoped server 可以写入 `.mcp.json`，适合团队共享；user/local scoped server 写入本机配置；MCP server 可以是 HTTP、stdio、WebSocket 等。([Claude Code][3])

示例：

```bash
# 本地 stdio MCP server
claude mcp add --transport stdio kca-tools -- python tools/mcp/kca_server.py

# 项目级，写入 .mcp.json
claude mcp add --transport stdio --scope project kca-tools -- python tools/mcp/kca_server.py

# 查看
claude mcp list
/mcp
```

MCP tool 暴露给 Claude 后，名字通常是：

```text
mcp__{server_name}__{tool_name}
```

官方 SDK custom-tools 文档也说明 MCP tools 暴露给 Claude 时使用这个命名格式。([Claude Code][2])

### Claude Agent SDK

在 SDK 里你通常这样注册：

```python
from claude_agent_sdk import tool, create_sdk_mcp_server, query, ClaudeAgentOptions

@tool(
    "kca_run_tests",
    "Run KCA tests in a sandboxed workspace.",
    {"selector": str},
)
async def kca_run_tests(args):
    # execute tests
    return {
        "content": [{"type": "text", "text": "pytest passed"}],
        "structuredContent": {"ok": True}
    }

kca_server = create_sdk_mcp_server(
    name="kca",
    version="1.0.0",
    tools=[kca_run_tests],
)

options = ClaudeAgentOptions(
    mcp_servers={"kca": kca_server},
    allowed_tools=["mcp__kca__kca_run_tests"],
)
```

官方文档说：定义 tool 后，要 wrap 到 `create_sdk_mcp_server` / `createSdkMcpServer`，再传给 `query()` 的 `mcpServers`；并且可以通过 `allowedTools` 控制 Claude 能访问哪些 tools。([Claude Code][2])

### KCA 平台

KCA 应该更进一步，做成三层 registry：

```text
ToolSpec registry:
  工具定义、schema、side_effect、timeout、sandbox、idempotency、permission label。

PermissionPolicy:
  allow / ask / deny，根据 job_type、competition policy、mode、人类审批状态决策。

ToolExecutor:
  真正执行工具，并写 audit/event/log。
```

也就是：

```text
Agent loop
  -> wants tool call
  -> KCA ToolRegistry validates name/schema
  -> PermissionPolicy resolves allow/ask/deny
  -> ToolExecutor runs in workspace/container
  -> Result + audit event + telemetry span
  -> Agent receives result
```

你当前 milestones 里也已经把 M3 worker 目标写成：worker 创建 isolated workspace/worktree、调用 KCA local tools、记录 job status/logs/artifacts/metrics、enforce max turns/cost/runtime/approval gates，并且 job 流程是 prompt → workspace → LLM tool loop → kca tool call → recorded result。

## 4. Agent 是否相当于平台，用来根据外部输入动态调用多个 skills 完成任务？

**概念上是，但要分清“agent loop”和“platform”。**

更准确地说：

```text
Agent loop:
  一轮轮调用模型，让模型读上下文、选择下一步、调用 tool、观察结果、继续。

Platform / harness:
  负责 queue、state、workspace、tool registry、permissions、budget、audit、UI、DB、approval gates。
```

Claude Agent SDK 官方说它把 Claude Code 的 tools、agent loop、context management 作为 Python/TypeScript 库暴露出来；agent 可以 autonomously read files、run commands、search web、edit code 等。([Claude Code][4]) 但生产系统不应该只靠这个 loop。KCA 的平台层应该决定：

```text
- 当前 job 可用哪些 skills；
- 当前 job 可用哪些 tools；
- 当前 job 的预算、turn limit、timeout；
- 哪些操作需要 approval；
- 结果如何验证；
- 失败如何重试；
- audit 如何落库；
- 何时 stop / pause / escalate。
```

KCA milestones 里已经把 north star 画成：Human/UI → TypeScript control plane（project/session/job/task queue、policy/approval gates、records/model router）→ Worker layer（Python Kaggle workers、Claude Agent SDK sessions、kca wrappers、browser tools、sandboxed execution/evaluation）→ External systems。

所以我会这样定义：

```text
Agent = 会思考和选择下一步的 worker
KCA Platform = 控制 agent 可以看到什么、做什么、何时停、如何证明成功的 harness
```

## 5. 外部输入不变时，skills 的调用顺序和具体调用是否可能不一样？

**会。尤其当你让模型自动选择 skill/tool 时，调用顺序不保证完全一致。**

原因包括：

```text
1. LLM 采样非完全确定，temperature/top_p/模型内部策略会影响选择。
2. skill 是通过 description 被 Claude 自动发现和加载，description 相近时可能触发不同。
3. 上下文不同：历史对话、已加载 skills、compact summary、tool results 都会改变下一步。
4. 工具环境不同：文件状态、git diff、CI 状态、网络/API 响应、时间都会改变路径。
5. tool list 过大时，模型选择工具的稳定性会下降。
6. Claude Code / model / MCP server 版本升级后，行为可能变化。
```

官方 skill 文档也说明，skill 的 description 帮助 Claude 决定何时自动加载；完整内容只在 invoked 时加载；一旦加载，skill 内容会作为消息留在 conversation context 中，compaction 时还会按预算重新附加最近 invoked skills。([Claude API Docs][1]) 这意味着同一个输入，只要“当前 session 中已加载过哪些 skill”不同，后续行为就可能不同。

所以对 KCA：

```text
如果稳定性重要：
  不要依赖 auto skill invocation。
  用 kca skill run <name> 显式调用。
  或让 JobSpec 固定 skill pipeline。
```

## 6. Skill 本身是不是也有不确定性？

**是。skill 只是 instructions + context，不是 deterministic program。**

即使你直接运行：

```text
/run-milestone M9-T002
```

也只是把 `SKILL.md` 内容送进模型上下文，模型仍然会决定：

```text
- 先读哪些文件；
- 调哪个 tool；
- 调几次；
- 如何解释测试失败；
- 何时认为 acceptance criteria 已满足。
```

Claude Code 文档里也说 bundled skills 是 prompt-based：它们给 Claude detailed instructions，然后让 Claude orchestrate work using tools；这和 built-in commands 的 fixed logic 不同。([Claude API Docs][1])

所以 skill 要写成：

```text
强约束 workflow，而不是自由发挥建议。
```

例如不要写：

```md
帮我完成 milestone。
```

而要写：

```md
1. Read task file.
2. Extract acceptance criteria.
3. Render plan JSON.
4. Run dry-run permission check.
5. Execute allowed local tools only.
6. Run tests.
7. Validate output schema.
8. If external side effect is needed, create decision record and stop.
9. Produce closeout.
```

Skill 可以降低 prompt 漂移，但不能消除模型不确定性。

## 7. 如何确保 agent 和 skill 稳定输出？是不是靠 harness engineering？

**是。稳定性主要靠 harness engineering，而不是靠“把 prompt 写得更长”。**

我建议 KCA 用下面这套稳定性层级。

### 第 1 层：固定输入和显式调用

```text
- 不靠 auto skill trigger，尽量显式 kca skill run <name>。
- JobSpec 固定 job_type、skill、model、temperature、max_turns、tools、policy。
- 输入文件、competition data、issue、task spec、commit SHA 都记录下来。
- 外部网页/API 结果 snapshot 或写入 research_items。
```

### 第 2 层：Skill 输出结构化

每个 skill 明确输出 schema：

```json
{
  "status": "success|blocked|needs_decision|failed",
  "summary": "string",
  "changed_files": ["string"],
  "tests_run": [
    {
      "command": "string",
      "result": "pass|fail|not_run",
      "evidence": "string"
    }
  ],
  "tool_calls": [
    {
      "tool": "string",
      "permission": "allow|ask|deny",
      "result": "ok|error"
    }
  ],
  "next_action": "string"
}
```

然后 harness 做 schema validation，不合格就 retry 或 fail。

### 第 3 层：Tool registry + permission policy

不要让 agent 随便 bash。让它优先调用稳定 tool：

```text
kca.tool.run_tests
kca.tool.record_metric
kca.tool.prepare_submission
kca.tool.create_decision
kca.tool.create_pr
```

每个 tool 要有：

```text
name
description
input_schema
output_schema
side_effect_level
timeout
idempotency
sandbox
permission_label
audit_required
```

KCA M7 的 exit criteria 已经要求：`kca skill list/show/run --dry-run`、permission policy allow/ask/deny、audit log records every tool execution、documentation explains Commands vs Skills vs Tools vs Jobs。

### 第 4 层：状态机而不是自由循环

不要让 agent 自己决定“下一步是什么”到无限自由度。KCA worker 可以定义：

```text
CREATED
  -> PLANNING
  -> TOOL_DRY_RUN
  -> EXECUTING_LOCAL
  -> TESTING
  -> REVIEWING
  -> WAITING_FOR_DECISION
  -> SUBMITTING
  -> CLOSED_SUCCESS / CLOSED_BLOCKED / CLOSED_FAILED
```

每个状态只允许有限动作。

### 第 5 层：Verifier / reviewer agent

对高风险路径，用独立 reviewer：

```text
implementation agent:
  产出 patch / artifact / submission.csv

reviewer agent:
  只读检查 acceptance criteria、tests、policy、artifact、score、risk

human gate:
  approve Kaggle submit / remote migration / merge
```

KCA M6/M9 的设计已经朝这个方向走：reviewer agent 在 high-stakes ops 前给出 approve/reject/abstain，M9 里真实 `kaggle competitions submit` 要经过 approved KCA approval gate 并记录 LB score。 

### 第 6 层：测试、golden cases、regression suite

每个 skill/tool/agent 都要有测试：

```text
skill parser tests
argument substitution tests
tool schema validation tests
permission policy tests
dry-run tests
golden prompt-output tests
end-to-end dry-run tests
approval gate tests
```

KCA 的 M12 也已经把可靠性目标写成：tool smoke tests、Kaggle practice tasks、notebook/kernel dry-run workflows、Claude/GPT/local model route regressions，并用 task completion rate、test pass rate、cost per successful run、human intervention count、approval gate correctness、artifact/log completeness 等指标评估。

## 8. 推荐的 KCA 抽象

我建议你最终把概念收敛成下面这张表：

| 概念      | 在 KCA 中是什么                            | 是否确定性 | 谁来验证                                         |
| ------- | ------------------------------------- | ----: | -------------------------------------------- |
| Command | `kca job run`, `kca decision approve` |     高 | CLI tests                                    |
| Skill   | `.kca/skills/run-milestone/SKILL.md`  |     中 | schema + dry-run + golden tests              |
| Tool    | `kca.run_tests`, `kca.kaggle_submit`  |     高 | input/output schema + unit/integration tests |
| MCP     | 外部 tool/data connector                |     中 | allowlist + output cap + sandbox + audit     |
| Agent   | 选择 skill/tool 的 LLM loop              |   低到中 | harness + reviewer + tests                   |
| Job     | 持久化 agent run                         |     高 | DB state machine + audit                     |
| Harness | queue/state/policy/test/audit/retry   |     高 | CI + regression suite                        |

## 9. 一个实用设计：Skill 可以声明需要哪些 tools，但不能直接拥有无限权限

```yaml
# .kca/skills/prepare-submission/SKILL.md
---
name: prepare-submission
description: Prepare and validate a Kaggle submission artifact without submitting it.
arguments:
  - run_id
required_tools:
  - kca.read_run
  - kca.validate_submission_file
  - kca.record_artifact
  - kca.triage_log
disallowed_tools:
  - kca.kaggle_submit
  - kca.kernel_push
side_effect_level: local-write
output_schema: skill_result_v1
---

Workflow:
1. Read run metadata.
2. Validate submission format.
3. Record artifact.
4. Produce JSON closeout.
5. If remote submission is requested, create decision gate and stop.
```

然后 Job Runner 做：

```text
load skill
  -> resolve required_tools against ToolRegistry
  -> resolve permission profile
  -> render prompt
  -> run agent loop with only those tools
  -> validate structured result
  -> persist audit/events/artifacts
```

这比“让 agent 自己发现所有 tools 和所有 skills”稳定得多。

## 10. 最终结论

你的理解方向是对的，但要加一个关键修正：

```text
Agent 不是稳定平台本身；
Agent 是平台里一个不完全确定的执行器。
真正的平台稳定性来自 harness。
```

所以：

```text
skills 可以组合，但不要依赖隐式互相调用；
tools 必须注册，并且要有 schema、权限、side-effect、timeout、audit；
agent 可以根据外部输入动态选择 skills/tools，但这天然不完全确定；
skill 也不完全确定，因为它仍由 LLM 执行；
稳定输出靠 harness engineering：
  explicit skill invocation
  small tool allowlist
  deterministic state machine
  schema validation
  dry-run mode
  approval gates
  tests/evals
  reviewer agent
  audit logs
  budget/turn/time limits
  workspace isolation
```

对 KCA，最稳的路线就是继续沿着 M7 的四层模型走：**Command 是确定入口，Skill 是 workflow recipe，Tool 是受控动作，Job 是 durable run；Agent 只是在 Job 里执行受控循环，不能绕过 ToolRegistry / PermissionPolicy / Audit / DecisionGate。**
