下面是我核对官方文档后的建议。先给结论：**你的方向基本对，但不要把“Claude CLI 7x24 自动排队开发”全部压在一个普通 CLI 会话上。**更稳的架构是：

**MacBook：Claude Code Desktop 做主开发与 review**；
**Arch Linux：Claude Code CLI / background agents 做长任务 runner**；
**真正无人值守、机器关机也能跑：Claude Code Routines / GitHub Actions / Claude Code Web cloud sessions**；
**想做成 Lovable 那种 prompt queue + 多轮迭代产品化系统：Claude Agent SDK 是最合适的底层。**

Claude Console 更偏 **API、prompt engineering、Workbench、billing、Managed Agents**，不是最适合作为“连接 repo 后像 IDE 一样开发”的主界面。Cursor 则是另一个很强的 IDE/agent harness；同一个 Opus 模型放在 Cursor 和 Claude Code 里，结果确实可能不同，因为差异不只是模型，还有工具、上下文检索、patch 策略、终端执行、权限、memory、测试循环等 harness engineering。Cursor 官方也明确把 agent 质量拆成 instructions、tools、model 这三层，并强调会针对不同 frontier model 调整 harness。([Cursor][1])

## 1. Arch Linux 上安装 Claude Code CLI 的步骤

官方目前给 macOS、Linux、WSL 的推荐安装方式是原生安装脚本：

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

也可以指定 stable 渠道；对长期 runner，我建议用 stable，减少最新版本回归风险：

```bash
curl -fsSL https://claude.ai/install.sh | bash -s stable
```

官方文档列出的 Linux 发行版是 Ubuntu / Debian / Alpine 等，Arch Linux 不在“明确列出”的发行版里，但这是 Linux 原生安装脚本；如果路径、依赖、shell 配置正常，通常可以工作。安装后用 `claude --version` 和 `claude doctor` 检查。Claude Code 需要 Claude Pro/Max/Team/Enterprise、Console/API 账号，或云服务商接入；Claude Pro 包含 Claude Code 访问，但不包含 Console API 计费额度。([Claude][2])

Arch 上我建议这样装：

```bash
sudo pacman -Syu

sudo pacman -S --needed \
  curl git github-cli openssh ripgrep tmux jq \
  base-devel python python-pip uv nodejs npm

curl -fsSL https://claude.ai/install.sh | bash -s stable

# 确保 ~/.local/bin 在 PATH 里；根据你的 shell 调整
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
exec "$SHELL" -l

claude --version
claude doctor
claude
```

第一次运行 `claude` 后按提示登录。Claude Code 也支持 `/login`，并会把认证信息保存在本机；可登录 Claude 订阅账号、Console/API 账号，或 Bedrock / Vertex / Foundry 等。([Claude API Docs][3])

连接 GitHub repo：

```bash
gh auth login
ssh-keygen -t ed25519 -C "arch-claude-runner"
cat ~/.ssh/id_ed25519.pub

# 把 public key 加到 GitHub 后：
mkdir -p ~/work
cd ~/work
git clone git@github.com:YOUR_ORG/YOUR_REPO.git
cd YOUR_REPO

gh repo view
claude
```

建议在 repo 根目录放一个 `CLAUDE.md`，让 Claude Code 每次进入项目时自动读项目规则。官方文档说明 `CLAUDE.md` 是 Claude Code 会在会话开始时加载的项目记忆文件，适合写常用命令、代码风格、测试方式、项目边界等。([Claude][4])

例如：

```md
# kaggle-code-agent project rules

## Goal
Build a code competition platform / agent runner for Kaggle-style coding tasks.

## Development loop
For every task:
1. Understand the objective.
2. Inspect existing architecture before editing.
3. Make minimal, testable changes.
4. Run relevant tests.
5. Summarize diff, tests, risks, and next tasks.

## Commands
- Unit tests: uv run pytest -q
- Type checks: uv run pyright
- Lint: uv run ruff check .
- Format: uv run ruff format .

## Safety
- Never commit secrets, API keys, Kaggle credentials, or .env files.
- Do not delete datasets, cached competition files, or experiment logs unless explicitly asked.
- Prefer feature branches and worktrees for independent tasks.
```

我也建议加 `.claude/settings.json`，限制危险操作。Claude Code 有多种权限模式，例如 `default`、`acceptEdits`、`plan`、`auto`、`dontAsk`、`bypassPermissions`；官方特别提醒 `bypassPermissions` 只适合隔离 VM 或容器。权限规则支持 allow / ask / deny，且 deny 优先级最高。([Claude][5])

示例：

```json
{
  "permissions": {
    "defaultMode": "auto",
    "allow": [
      "Bash(git status*)",
      "Bash(git diff*)",
      "Bash(git log*)",
      "Bash(pytest *)",
      "Bash(python *)",
      "Bash(uv run *)",
      "Bash(ruff *)"
    ],
    "ask": [
      "Bash(git push*)",
      "Bash(gh pr create*)",
      "Bash(gh pr merge*)",
      "Bash(rm *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)",
      "Bash(sudo *)",
      "Bash(rm -rf /*)",
      "Bash(curl * | bash*)"
    ]
  }
}
```

## 2. Arch Linux 上 7x24 工作：可以，但要分清“本机长跑”和“云端无人值守”

Claude Code 现在有 background agents。你可以在 CLI 中打开 agent 视图：

```bash
cd ~/work/YOUR_REPO
claude agents
```

也可以直接从 shell 启动后台任务：

```bash
claude --bg \
  --name "feature-eval-loop-001" \
  --permission-mode auto \
  --model opus \
  --effort high \
  "/goal implement the evaluation harness described in docs/eval.md. Keep working until uv run pytest -q passes and the CLI demo works, or stop after 50 turns and summarize blockers."
```

官方文档说，background session 不需要终端窗口保持打开；它们由单独的 supervisor process 管理，并且可以用 `claude agents`、`claude attach`、`claude logs`、`claude stop` 等命令查看、接入或停止。每个 background prompt 会开启一个独立 session；在 git repo 内，它会使用隔离的 git worktree，避免多个 agent 同时改同一工作目录。([Claude][6])

但是，**Arch 机器如果睡眠、关机、断网，local background sessions 会停**。官方文档也说明机器 sleep / shutdown 后 session 会停止，可用 `claude respawn --all` 恢复。因此你的 Arch Linux runner 适合放在 always-on 机器、VPS、homelab server，或者不开睡眠的 workstation 上。([Claude][6])

推荐用 `tmux` + `loginctl enable-linger`：

```bash
loginctl enable-linger "$USER"

tmux new -s claude
cd ~/work/YOUR_REPO
claude agents --permission-mode auto --model opus --effort high
```

常用管理命令：

```bash
claude agents              # 查看 agent 列表
claude logs <session-id>   # 看日志
claude attach <session-id> # 接入某个 session
claude stop <session-id>   # 停止
claude respawn --all       # 机器恢复后重启可恢复的 background sessions
```

如果你的要求是“我的 MacBook 关了、Arch 也不稳定，但任务仍要持续排队跑”，那应该用 **Claude Code Routines / GitHub Actions / Claude Code Web cloud sessions**。官方文档说明 Routines 可在 Anthropic infra 上按 schedule、GitHub event 或 API trigger 运行；Desktop task 是本机，`/loop` 是 CLI 内重复，而 Routines 是云端执行，适合电脑不在线时继续跑。([Claude][7])

## 3. 能不能像 Lovable 一样 queue prompts，每个 task 跑 30–100 轮直到完成？

**可以接近实现，但要选对层。**

### 3.1 普通 Claude CLI 单会话：不是 Lovable queue

单个普通 `claude` 会话更像一个 interactive coding assistant。你可以不断给它任务，但它不是天然的产品级任务队列。

### 3.2 Claude Code `/goal`：最接近“直到完成”的内置能力

Claude Code 有 `/goal`。它可以设置一个 completion condition，让 Claude 在多轮中持续工作，直到条件满足。官方示例包括“直到测试通过”“直到迁移完成”“直到 issue backlog 完成”等；也可以加停止条件，比如 “or stop after 20 turns”。([Claude][8])

例如：

```text
/goal implement the Kaggle submission runner until:
- uv run pytest -q passes
- examples/local_smoke_test.py succeeds
- docs/runner.md explains usage
- no secrets are committed
or stop after 60 turns and summarize blockers.
```

你也可以用 print mode 非交互执行：

```bash
claude -p "/goal implement the leaderboard ingestion module until uv run pytest -q passes or stop after 40 turns"
```

不过要注意：CLI 的 `--max-turns` 是 print mode 的参数，不是所有 interactive/background agent 的通用限制。更稳的方式是在 `/goal` 里写清楚 “or stop after N turns”，或者用 Agent SDK 自己实现轮数、预算、重试和验收逻辑。Claude CLI 参数里也有 `--max-budget-usd`、`--max-turns`、`--model`、`--permission-mode` 等可用选项。([Claude][9])

### 3.3 Claude Code background agents：可以把每个 prompt 当成一个 queued task

你可以这样跑多个任务：

```bash
claude --bg --name "task-api-refactor" \
  "/goal refactor the API layer according to docs/api_refactor.md until tests pass or stop after 50 turns"

claude --bg --name "task-kaggle-runner" \
  "/goal implement Kaggle runner v1 until local smoke test passes or stop after 80 turns"

claude --bg --name "task-eval-dashboard" \
  "/goal build the evaluation dashboard skeleton until npm test passes or stop after 40 turns"
```

这已经很像“prompt queue”，但它还是偏 operator workflow：你通过 shell 启动任务，通过 `claude agents` 管理。它适合你个人开发，不一定适合作为最终平台。

### 3.4 `/loop`：适合定时检查，不适合 durable queue

Claude Code 还有 `/loop`，可以按固定或动态间隔重复执行 prompt，比如定时检查 PR、继续未完成工作、清理失败任务。但官方文档说明 `/loop` 是 session-scoped，任务只有在 Claude Code 正在运行且空闲时触发，不会补跑 missed runs，循环任务也有过期限制；无人值守场景官方更建议 Routines、Desktop scheduled tasks 或 GitHub Actions。([Claude][10])

### 3.5 真正 Lovable-style queue：用 Claude Agent SDK

如果你要做的是 **kaggle-code-agent / code competition platform**，我会把 Claude Code CLI 当成开发工具，把 **Claude Agent SDK** 当成产品化 agent runner 的核心。

Agent SDK 官方描述是：把驱动 Claude Code 的 tools、agent loop、context management 暴露成 Python / TypeScript SDK；可以读写文件、运行命令、搜索、编辑代码。Python SDK 支持 `query()` 一次性任务，也支持 `ClaudeSDKClient` 做持续会话；TypeScript SDK 也可安装 `@anthropic-ai/claude-agent-sdk`。([Claude API Docs][11])

你可以自己实现：

```text
Task table:
- id
- repo
- branch/worktree
- prompt
- max_turns
- max_budget
- status
- logs
- test_command
- acceptance_criteria
- created_at
- completed_at
```

每个 task：

```text
1. checkout repo
2. create isolated branch/worktree/container
3. call Agent SDK
4. run model loop
5. run tests/evals after each major edit
6. stop when acceptance criteria passes or max_turns/max_budget reached
7. produce patch / PR / report
8. require human approval before merge
```

官方 Agent SDK 文档也提醒：如果 agent 要执行命令，应该运行在 sandboxed container / isolated environment 里；权限审批和用户输入也要由你的应用层负责呈现。([Claude][12])

## 4. Claude Console 能连接 GitHub repo 进行开发吗？更适合你的需求吗？

这里要区分三个东西：

### Claude Console / Anthropic Console

Claude Console 主要是 API 平台：创建 API key、用 Workbench 试 prompt、管理模型调用、使用 Messages API、Batches、Files、Skills、Agents API、Sessions API 等。官方 prompt 工具包括 prompt generator、templates、variables、prompt improver。它适合 **prompt engineering、API 原型、评估、计费和 Managed Agents 开发**，但不是最适合你日常“打开 repo、改代码、跑测试、提 PR”的开发界面。([Claude API Docs][13])

### Claude.ai 的 GitHub integration

Claude.ai 支持把 GitHub repo 或文件作为 chat / project context 添加进去，用来问代码、分析文件、补充上下文。它可以连接 private repo，但受上下文窗口限制，多个 repo 或大量文件需要选择性加入。它更像“把 repo 内容作为知识上下文”，而不是完整的 autonomous coding harness。([Claude Help Center][14])

### Claude Code Web / Routines / GitHub Actions

如果你想让 Claude 在云端 clone repo、改代码、push branch、开 PR，那么应该看 **Claude Code Web、Routines、GitHub Actions**。Claude Code Web cloud sessions 可在 Anthropic-managed VM 上运行，浏览器关闭后 session 仍可继续；云端 session 需要 GitHub access 来 clone/push repo。Routines 则可以用 schedule、GitHub event、API trigger 启动，并在 Anthropic infra 上运行。([Claude][15])

所以答案是：

**Console 本身不更适合你的 repo 开发主流程。**
**Claude Code Web / Routines / GitHub Actions 更适合你的 7x24 GitHub repo 自动开发需求。**
**Console 更适合你做 API prompt、模型调用、agent backend 实验和账单管理。**

## 5. Cursor 连接 Opus 4.6 / 4.7，和 Claude Code 的主要区别是什么？

你的理解基本正确：**很大一部分区别就是 harness engineering。**

同样是 Claude Opus 4.7，放在 Cursor、Claude Code、Agent SDK、自研 harness 里，结果可能不同。Anthropic 官方称 Opus 4.7 是面向复杂推理和 agentic coding 的高能力模型，支持 1M context、128k output、adaptive thinking、task budgets 等新能力；但模型只是其中一层。([Claude][16])

Cursor 的 CLI / IDE 支持多家 frontier models，包括 Anthropic、OpenAI、Gemini、Cursor 自家模型；Cursor CLI 文档示例里可以选择 `Opus 4.7`，也支持脚本、shell mode、GitHub Actions 等。Cursor 也支持 BYOK，用自己的 OpenAI / Anthropic / Google / Azure / Bedrock API keys。([Cursor][17])

Claude Code 和 Cursor 的差异主要在这些层：

| 层    | Claude Code                                                    | Cursor                                                |
| ---- | -------------------------------------------------------------- | ----------------------------------------------------- |
| 主定位  | 终端 / Desktop / Web / GitHub / SDK 的 agentic coding system      | IDE-first coding environment + agent                  |
| 代码操作 | CLI、Desktop diff、background agents、Routines、SDK                | IDE 编辑、inline completion、Agent、Plan Mode、Cloud Agents |
| 上下文  | Claude Code 的 repo reading、memory、CLAUDE.md、tool loop、worktree | Cursor 的 codebase index、rules、plans、IDE context       |
| 长任务  | `/goal`、`/loop`、background agents、Routines、GitHub Actions      | Agent / Plan Mode / Cloud Agents，也可长时间跑               |
| 自动化  | CLI、GitHub Actions、Routines、Agent SDK 很强                       | Cursor CLI、Background/Cloud agents、IDE 自动化强           |
| 产品化  | Agent SDK 更直接                                                  | 更适合开发者工具/IDE 工作流                                      |
| 人机协作 | Desktop/CLI/Web review                                         | IDE 内体验更自然，Tab/inline 强                               |

所以，**生成代码质量确实可能不一样**，不是因为 Opus 4.7 在某个平台“智商不同”，而是因为：

1. 哪些文件被放进上下文不同。
2. code search / grep / AST / terminal tools 不同。
3. patch 生成和应用方式不同。
4. 是否会自动运行测试不同。
5. memory / project rules / system prompt 不同。
6. 权限和安全策略不同。
7. 长任务中如何压缩上下文、恢复状态、决定下一步不同。
8. 出错后是否能自动 debug、重跑、回滚不同。

对你来说，Cursor 很适合做 **IDE-first 的人工协同开发**；Claude Code 更适合做 **terminal-first、repo automation、background agents、GitHub PR、SDK 自研 agent runner**。

## 6. 五个工具的对比

| 工具                               | 本质                                       | 能否连接 / 操作 repo                         | 长任务 / 队列能力                                        | 最适合你的用途                              | 主要注意点                          |
| -------------------------------- | ---------------------------------------- | -------------------------------------- | ------------------------------------------------- | ------------------------------------ | ------------------------------ |
| **Claude Code CLI / Claude CLI** | `claude` 终端 agent                        | 可以在本地 repo 里读写文件、运行命令、创建分支             | `/goal`、`--bg`、`claude agents`、`/loop`、print mode | Arch Linux runner、长任务、自动测试、批量改代码     | 本机断电/睡眠会停；权限要管好                |
| **Claude Code Desktop**          | GUI 版 Claude Code                        | 可本地、cloud、SSH；可看 diff、预览 app、多 session | 多 session、云/本地任务、review 体验好                       | MacBook 主开发、review、调 prompt          | 不如 CLI/SDK 适合脚本化队列             |
| **Claude Console**               | API / Workbench / prompt tools / billing | 更偏 API 和 context，不是 IDE 式 repo 开发      | API / Managed Agents / Sessions，可开发自研 agent       | prompt engineering、API 实验、评估、账单      | 不应作为主要 coding UI               |
| **Cursor**                       | IDE-first AI coding environment          | 强，直接在 IDE repo 中工作                     | Agent、Plan Mode、Cloud Agents、CLI                  | 人工协同开发、inline completion、快速 refactor | harness 与 Claude Code 不同，结果会不同 |
| **Claude Agent SDK**             | 可编程 Claude Code agent loop               | 由你决定如何 clone repo、开容器、跑测试、提 PR         | 最适合自定义 queue、max turns、budget、approval、logs       | 构建 kaggle-code-agent 平台本体            | 你要自己做 sandbox、安全、队列、UI、审计      |

## 7. 针对你的项目，我建议的工作流

### A. 日常开发

用 **Claude Code Desktop on MacBook** 做主开发和 review。它支持多 session、diff review、preview app、连接 GitHub / Slack / Linear、本地 / cloud / SSH 等工作方式，适合你在 Mac 上把控代码方向和审查结果。([Claude][18])

ChatGPT Pro 负责：

```text
1. 拆解 milestone
2. 写清晰 task prompt
3. 定义验收标准
4. 生成 Claude Code /goal prompt
5. 设计测试策略
6. review Claude 的总结和 patch 风险
```

### B. Arch Linux 作为 long-running runner

Arch 上跑：

```bash
cd ~/work/kaggle-code-agent
claude agents --permission-mode auto --model opus --effort high
```

每个任务都用 `/goal` 包住：

```text
/goal Implement task X until:
- uv run pytest -q passes
- the smoke test command succeeds
- no secrets are introduced
- git diff only touches relevant files
or stop after 80 turns and summarize blockers.
```

### C. 真正 7x24 / 不依赖本机

用 **Claude Code Routines 或 GitHub Actions**。Routines 可以按 schedule、GitHub event、API trigger 跑，并在云端创建 session、review changes、create PR。对“每天检查 issue backlog”“收到 GitHub issue 后自动开 branch 实现”“定时跑 benchmark 并修复失败”这种需求，比本地 CLI 更合适。([Claude][7])

### D. 做成 Lovable-style prompt queue

用 **Claude Agent SDK**，不要只依赖 CLI。CLI 是很好的 operator tool；SDK 才适合你做平台化：

```text
User prompt
  -> task queue
  -> repo clone / worktree / container
  -> Agent SDK session
  -> iterative coding loop
  -> tests / evals / benchmark
  -> patch / branch / PR
  -> human approval
  -> merge / archive logs
```

### E. Cursor 的位置

Cursor 可以作为补充，而不是替代所有东西：

* 想要 IDE 里快速改代码、补全、局部 refactor：用 Cursor。
* 想要 autonomous repo task、background agent、GitHub PR automation：用 Claude Code。
* 想要自研 code competition agent platform：用 Claude Agent SDK。
* 想要 prompt / API 实验：用 Claude Console。
* 想要 ChatGPT 帮你写任务说明、架构计划、Claude prompts：继续用 ChatGPT Pro。

## 8. 我的推荐组合

对你的 `kaggle-code-agent`，我会这样配：

```text
Planning / prompt writing:
  ChatGPT Pro

Human-in-the-loop development:
  Claude Code Desktop on MacBook
  Cursor 可选，用于 IDE-first editing

Always-on local runner:
  Arch Linux + Claude Code CLI + background agents + /goal
  repo 使用 git worktree / branch isolation

True cloud automation:
  Claude Code Routines 或 GitHub Actions

Productized prompt queue:
  Claude Agent SDK + containers + DB queue + test/eval harness + PR workflow

API / prompt / billing:
  Claude Console
```

一句话：**Claude Code CLI/desktop 用来开发，Routines/GitHub Actions 用来无人值守，Agent SDK 用来把“Lovable-style 多轮任务队列”做成你自己的平台，Console 用来做 API/prompt 管理，Cursor 用来补 IDE 体验。**

⚡️Q: 好的，我现在安装了 Claude Code for VS Code (macbook) 的插件，这个编写代码能力应该和 Claude Code desktop 差不多吧。Lovable 后面是不是用的就是 Claude Agent SDK ? 另外我也打开了 ArchLinux + screen + Claude CLI 在当前项目目录中，Claude Code Web 也已经 setup 好了，应该可以让 Claude Code 开始开发了。这样我 3 个终端 应该可以同步了吧，还有什么需要注意的？

对，现在这个配置已经可以让 Claude Code 开始开发了。不过我要把“同步”说清楚：

**VS Code 插件、Arch Linux Claude CLI、Claude Code Web 不是天然共享同一个实时会话。**
它们真正可靠的同步层应该是：**GitHub repo + branch / worktree + PR + CI**。
同一台机器上的 VS Code 插件和 CLI 可以共享本地对话历史与设置；Claude Code Web 是云端 session；Arch Linux CLI 是另一台机器上的本地 session。三者可以协同，但不要让它们同时改同一个 branch / 同一批文件。

## 1. Claude Code for VS Code 的编写代码能力，和 Desktop 差不多吗？

**核心 coding agent 能力是同一类，日常写代码可以认为接近；但界面能力不完全一样。**

Claude Code VS Code 插件是官方推荐的 VS Code 使用方式，支持图形化面板、review / edit plan、auto-accept edits、`@` 文件和行号引用、conversation history、多 conversation tab/window 等；它还内置 CLI，可以在 VS Code integrated terminal 中使用更高级的 CLI 功能。([Claude][1])

区别主要是产品表面层：官方平台说明里明确说 **CLI 是 terminal-native 工作最完整的 surface**，scripting 和 Agent SDK 是 CLI-only；Desktop / IDE extensions 则用一些 CLI-only 能力换来更强的视觉 review 和 IDE 集成；Web 跑在 Anthropic cloud 上，断开连接后任务还能继续。([Claude][2])

Desktop 的强项是多 session 侧栏、集成 terminal/file editor、visual diff review、live app preview、GitHub PR monitoring / auto-merge、scheduled tasks 等；Code tab 是直接访问本地文件的 interactive coding assistant，改动需要你 review/approve。([Claude][3])

所以你的用法可以这样理解：

```text
VS Code 插件：
  最适合日常人工协同开发、局部修改、review diff、@文件/行号提问。

Claude Code Desktop：
  更适合多 session 可视化管理、preview、PR 监控、scheduled task 等桌面工作流。

Claude CLI：
  最适合脚本化、后台任务、agent view、worktree 并行、自定义自动化。

Claude Code Web：
  最适合云端无人值守、从任何设备查看、并行 remote task、PR auto-fix。
```

如果你已经在 VS Code 中开发，**没有必要因为“代码质量”单独切到 Desktop**。真正影响质量的是：prompt、`CLAUDE.md`、测试命令、上下文、branch/worktree 隔离、是否让它跑 CI/pytest、是否有明确验收标准。

## 2. Lovable 后面是不是用 Claude Agent SDK？

**公开资料不能证明 Lovable 后面就是 Claude Agent SDK。**更准确地说：Lovable 明确使用 Claude / Claude Platform，但没有看到官方资料说它使用 Claude Agent SDK。

Anthropic 的 Lovable customer story 说，Lovable uses Claude to transform software development，并且产品字段是 **Claude Platform**；Lovable 选择 Claude 作为核心产品中的可靠代码生成能力来源。([Claude][4]) Lovable 自己的安全文章又说它采用 multi-provider AI strategy，包括 Anthropic Claude、Google Vertex AI、OpenAI、AWS Bedrock，并有 routing/fallback。([Lovable][5]) Lovable 文档还描述了 Agent Mode：独立 codebase exploration、debugging、web search、automated problem-solving，并通过 queued execution model 端到端处理任务。([Lovable][6]) 最新 changelog 也显示 Lovable Agent 已经 incorporates Claude Opus 4.7。([Lovable Documentation][7])

但这些都只说明：**Lovable 有自己的 agent harness / queue / execution platform，并使用 Claude 等模型。**
它是否直接用了 Claude Agent SDK，没有公开证据。考虑到 Lovable 早于 Agent SDK 大规模成熟期，而且有自己的云平台、diff viewer、Supabase/hosting/security/product workflow，很可能是 **自研 harness + Claude API / 多模型 routing**，现在也可能吸收了类似 Agent SDK 的思路。

Claude Agent SDK 官方定位是“把 Claude Code 背后的 tools、agent loop、context management 作为 Python / TypeScript 库开放”，可让 agent 读文件、跑命令、搜索、编辑代码。([Claude][8]) 所以结论是：

```text
Lovable 不一定用 Claude Agent SDK；
但你要做 kaggle-code-agent / prompt queue / multi-turn coding runner，
Claude Agent SDK 是最接近 Lovable-style agent backend 的官方底层之一。
```

## 3. 你现在的三个环境能同步吗？

**可以协同，但不是自动实时同步。**

### 情况 A：VS Code 插件 ↔ Mac 上的 Claude CLI

这个可以比较紧密。VS Code 插件和 CLI 在同一台机器上共享 conversation history；你可以在 CLI 里用 `claude --resume` 选择继续插件里的 conversation。插件和 CLI 的 Claude Code settings 也共享，例如 `~/.claude/settings.json` 里的 allowed commands、env、hooks、MCP servers。([Claude][1])

### 情况 B：Arch Linux Claude CLI ↔ MacBook VS Code

这两个**不会共享本地 Claude 会话历史**。它们同步代码的方式应该是 GitHub：

```bash
git pull --rebase
git checkout -b claude/<task-name>
# run Claude task
git push origin claude/<task-name>
gh pr create
```

Arch 上跑的 Claude 会话、Mac 上跑的 Claude 会话，是两个独立上下文。要让它们理解同一套项目规则，最重要的是把这些放进 repo：

```text
CLAUDE.md
docs/tasks/*.md
docs/architecture.md
docs/testing.md
.github/workflows/*
```

Claude Code 每个新 session 默认是 fresh context，历史不会自动进入新 session；持久规则应该放在 `CLAUDE.md`，也可以用 memory。([Claude][9])

### 情况 C：Claude Code Web ↔ 本地 CLI

Claude Code Web 是 cloud session。它运行在 Anthropic-managed cloud infrastructure，浏览器关了 session 仍可持续，你也可以用手机监控。([Claude][10])

从 terminal 发 cloud task 时可以用：

```bash
claude --remote "Implement the task in docs/tasks/T001.md and open a PR"
```

但注意：`--remote` 会从 GitHub remote clone 当前 repo / branch，所以**本地 commit 必须先 push**，否则 cloud VM 看不到你的本地改动。官方文档也强调它 clone 当前目录的 GitHub remote/current branch，并建议 push first。([Claude][10])

Web session 做完后，可以从本地拉回继续：

```bash
git status
# 工作区必须干净，必要时先 stash
claude --teleport
```

`--teleport` 会拉取 cloud session 的 branch 和 conversation history；要求 clean git state、同一个 repo、cloud session branch 已 push、同一个 claude.ai account。([Claude][10])

### 情况 D：Remote Control 和 Claude Code Web 不一样

如果你想让 Web / 手机只是“远程控制 Arch 或 Mac 上正在跑的本地 Claude session”，那用的是 **Remote Control**，不是普通 Claude Code Web cloud session。Remote Control 的特点是 session 仍跑在你的机器上，web/mobile 只是窗口，并且 terminal/browser/phone 的 conversation 会同步。([Claude][11])

在 Arch 上可以考虑：

```bash
cd ~/work/kaggle-code-agent
claude remote-control
```

然后你可以从 claude.ai/code 或手机接入这个 Arch 本地 session。但这和 cloud session 的区别很大：Remote Control 依赖 Arch 机器继续运行；Claude Code Web cloud session 不依赖你的机器。

## 4. 最重要的注意事项：不要三个 Claude 同时改同一个 branch

你现在最大风险不是“能不能开工”，而是：

```text
Mac VS Code Claude 正在改 src/agent_runner.py
Arch CLI Claude 也在改 src/agent_runner.py
Claude Code Web 又从旧 branch clone 了一份继续改
```

最后会变成冲突、重复实现、测试状态混乱、Claude 彼此覆盖。

建议你立刻采用这个规则：

```text
main:
  永远只作为稳定 base，不让 agent 直接改。

每个 Claude task:
  一个独立 branch / worktree / PR。

同一个 branch:
  同一时间只允许一个 Claude session 修改。

合并方式:
  PR + CI + 人类 review，然后 main 更新，其他 branch rebase。
```

Claude Code 官方也建议用 git worktrees 做并行任务；每个 worktree 是独立 checkout 和独立 branch，避免 edits collision。([Claude][12]) VS Code 文档里也有 `claude --worktree feature-auth`，说明 isolated worktree 可防止 Claude instances 互相干扰。([Claude][1])

在 Arch 上可以这样开任务：

```bash
cd ~/work/kaggle-code-agent
git checkout main
git pull --rebase

claude --worktree task-eval-harness
```

或者用 background agents：

```bash
cd ~/work/kaggle-code-agent
claude agents
```

每次在 agent view 输入一个 prompt 会启动一个新的 background session，而不是给当前 session 发 follow-up；后台 session 会继续运行，你可以 later attach。([Claude][13]) 后台 session 在改文件前会进入 `.claude/worktrees/` 下的 isolated git worktree，所以本地并行任务相对安全。([Claude][13])

## 5. 我建议你的三环境分工

### MacBook VS Code 插件：主控与 review

用它做：

```text
- 读代码
- 小改动
- review Claude 的 plan
- review diff
- 写 CLAUDE.md / docs/tasks/*.md
- 合并前最终确认
```

推荐 prompt：

```text
Read CLAUDE.md and docs/tasks/T001.md.
First inspect the current architecture.
Do not edit files yet.
Produce a concise implementation plan with:
- files to change
- tests to add
- risks
- acceptance criteria
Wait for my approval before editing.
```

### Arch Linux + screen + Claude CLI：长任务 runner

用它做：

```text
- background agents
- pytest/debug loop
- 数据处理脚本
- 长时间 refactor
- CI failure 修复
```

建议不要只依赖 screen 里的普通 interactive `claude`。更适合：

```bash
cd ~/work/kaggle-code-agent
claude agents --model opus --permission-mode auto
```

或者：

```bash
claude --bg \
  --name "T001-eval-harness" \
  --model opus \
  --permission-mode auto \
  "/goal implement docs/tasks/T001.md until uv run pytest -q passes or stop after 60 turns and summarize blockers"
```

普通直接运行的 `claude` session 是 tied to terminal；background sessions 则由 per-user supervisor process 承载，和 terminal/agent view 分开。([Claude][13])

### Claude Code Web：云端无人值守 / PR 修复

用它做：

```text
- 明确、独立、可验收的 task
- cloud session
- PR auto-fix
- CI failure repair
- 不依赖 Arch/Mac 在线的工作
```

从本地发 cloud task 前：

```bash
git status
git add CLAUDE.md docs/tasks/T001.md
git commit -m "Add task T001 spec"
git push origin <branch>

claude --remote "Execute docs/tasks/T001.md. Run tests and open a PR."
```

对于已有 PR，可以考虑 `/autofix-pr`。官方命令说明是：它会 spawn Claude Code on the web session，watch 当前 branch 的 PR，在 CI fail 或 reviewer comments 出现时 push fixes；需要 `gh` CLI 和 Claude Code on the web access。([Claude][14])

## 6. 现在开工前，我建议你补齐 8 个 guardrails

### 1. 建立 `CLAUDE.md`

最重要。写清楚：

```text
- 项目目标
- 禁止事项
- branch/PR 规则
- 测试命令
- lint/typecheck 命令
- 如何运行 smoke test
- Kaggle credentials 不能读取/提交
- 每次任务完成必须总结 diff/tests/risks
```

### 2. 建立 `docs/tasks/`

每个任务一个 markdown 文件：

```text
docs/tasks/T001-eval-harness.md
docs/tasks/T002-repo-runner.md
docs/tasks/T003-kaggle-submission-loop.md
```

每个文件包含：

```text
Goal
Non-goals
Context
Files likely involved
Acceptance criteria
Commands to run
Expected output
Stop conditions
```

### 3. 开 GitHub branch protection

至少：

```text
- main 禁止 direct push
- required CI checks
- PR review required
- no force-push to main
```

### 4. 让每个 agent 只改自己的 branch

命名建议：

```text
claude/vscode/T001-plan
claude/arch/T002-eval-harness
claude/web/T003-ci-fix
```

### 5. 不要把 secrets 暴露给 Claude

尤其是：

```text
.env
KAGGLE_USERNAME
KAGGLE_KEY
ANTHROPIC_API_KEY
GitHub PAT
AWS keys
```

`.gitignore` 和 `.claude/settings.json` 都要管。比如：

```json
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)",
      "Bash(sudo *)",
      "Bash(rm -rf /*)"
    ],
    "ask": [
      "Bash(git push*)",
      "Bash(gh pr create*)",
      "Bash(rm *)"
    ]
  }
}
```

### 6. 每个任务 prompt 必须带停止条件

例如：

```text
/goal Implement docs/tasks/T001-eval-harness.md until:
- uv run pytest -q passes
- uv run ruff check . passes
- a smoke test demonstrates the feature
- git diff only touches relevant files
or stop after 60 turns and summarize blockers.
```

### 7. 每轮合并后，所有环境都 pull/rebase

在 Mac、Arch、本地 cloud teleport 前都先：

```bash
git status
git fetch origin
git checkout main
git pull --rebase
```

其他 feature branch：

```bash
git fetch origin
git rebase origin/main
```

### 8. 控制并发数量

一开始不要同时开太多。建议：

```text
第 1 周：
  1 个 Arch background task
  1 个 Web cloud task
  Mac VS Code 只做 review/planning

稳定后：
  2-3 个 Arch background tasks
  1-2 个 Web cloud tasks
```

Claude Code 支持并行，但项目早期架构还不稳定时，过多 agent 会制造重复抽象和冲突。

## 7. 一个适合你现在马上执行的启动流程

在 repo 里先做：

```bash
git checkout main
git pull --rebase
mkdir -p docs/tasks
```

创建：

```text
CLAUDE.md
docs/tasks/T001-project-baseline.md
```

`T001-project-baseline.md` 可以写：

```md
# T001 Project baseline

## Goal
Inspect the current repository and create a reliable development baseline for kaggle-code-agent.

## Tasks
1. Understand the current architecture.
2. Identify missing tests, missing docs, dependency issues, and unclear entrypoints.
3. Add or update only lightweight baseline files:
   - README.md if needed
   - CLAUDE.md if needed
   - docs/architecture.md
   - docs/testing.md
4. Do not implement major features yet.

## Acceptance criteria
- `uv run pytest -q` or the documented test command runs successfully, or blockers are documented.
- `docs/architecture.md` explains the current modules.
- `docs/testing.md` explains how to run tests and smoke checks.
- No secrets or credentials are read or committed.

## Stop condition
Stop after 30 turns if the repo structure is unclear and summarize blockers.
```

然后在 Arch：

```bash
git checkout -b claude/arch/T001-project-baseline
claude --bg \
  --name "T001-project-baseline" \
  --permission-mode auto \
  "/goal Execute docs/tasks/T001-project-baseline.md until acceptance criteria pass or stop after 30 turns and summarize blockers"
```

在 Mac VS Code 里只做 review，不同时改同一 branch。等 Arch 推 PR 后，你在 VS Code 插件里让 Claude review：

```text
Review the PR branch claude/arch/T001-project-baseline.
Focus on:
- whether docs match the actual repo
- whether tests are correctly documented
- whether any secrets or irrelevant files were touched
Do not edit files yet; produce review comments first.
```

## 8. 我的判断

你现在的 setup 是一个很好的组合：

```text
VS Code Claude Code:
  主开发 + review

Arch Linux Claude CLI:
  长任务 + background agents + worktree 并行

Claude Code Web:
  云端 task + PR autofix + 不依赖本机在线

ChatGPT Pro:
  任务拆解 + prompt 写作 + 架构/验收标准设计
```

真正需要注意的是：**把“同步”理解成 GitHub/PR 级别同步，而不是会话实时同步。**
只要做到 **每个 task 一个 branch/worktree、每个 prompt 有验收标准、main 受保护、secrets 禁止读取、CI 必跑**，就可以开始让 Claude Code 干活了。
