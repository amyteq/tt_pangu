# A1:
根据 2026-05-23 的项目文档，我的总体判断是：**你现在的方向是对的，但需要把“比赛实践层”和“KCA 能力层”明确分开**。`competitions/` 应该成为真实比赛的压缩记忆与证据层；`.kca/skills/`、`tools/kca/`、worker、permission policy 才是 KCA 能力层。中间用一套“insight → skill candidate → issue/PR → test/eval → promoted”的流程连接。

你的项目文档本来就把 KCA 定义成一个让人和 AI code agents 协作参加 code competitions 的平台，核心能力包括研究比赛规则/数据/notebooks/discussions/baselines、创建和迭代代码、跟踪 experiments/artifacts/results/submissions/analysis，并在 Kaggle submission 或 kernel push 等外部副作用前要求人工批准。 同时，项目也明确说 GitHub repo 是 durable source of truth，AI 隐藏记忆不可靠，所以这些比赛经验应该沉淀到 repo 文件，而不是长期依赖 issue comments 或某次 Claude 会话。

## 1. 什么时候、如何让 KCA 提取具体比赛的 common skills？

我建议不要让 KCA “实时从每条讨论中自动升级自己”。更好的节奏是 **分层、分阶段提取**：

```text
比赛执行中：
  只更新 competition docs / tasks / runs / submissions / bugs

阶段性复盘：
  提取 competition-specific insights

跨比赛复盘：
  提取 common skill candidates

KCA 能力升级：
  通过 issue → PR → tests/evals → merge
```

也就是：

### 阶段 A：比赛运行中，只做“压缩记忆”，不升级 KCA

每次 Claude Code 完成一个具体任务，例如 Orbit baseline、Nemo notebook 修复、一次 submit/push、一次 LB 分析，只要求它更新对应比赛目录里的：

```text
status snapshot
tasks / progress
submissions log
bugs
references
insights
```

这个阶段的目标是减少 token、减少长 issue 依赖。不要让它马上改 `.kca/skills/` 或 `tools/kca/`。

### 阶段 B：出现一个稳定里程碑后，做一次 competition postmortem

触发条件可以是：

```text
- 第一个可运行 baseline 完成
- 第一次合法 submission 完成
- 3-5 个 experiment 后
- 一次明显失败/事故后
- 比赛每 2-3 天一次
- 比赛结束或阶段收尾
```

每次 postmortem 输出到：

```text
competitions/<slug>/postmortems/YYYY-MM-DD-<topic>.md
```

格式建议：

```md
# Postmortem: <topic>

## What changed

## Metrics
- local CV:
- public LB:
- runtime:
- cost:
- submission id / kernel version:

## What worked

## What failed

## Root causes

## Reusable patterns

## Competition-specific only

## Candidate KCA improvements
- [ ] skill candidate:
- [ ] tool candidate:
- [ ] policy/checklist candidate:
- [ ] test/eval candidate:

## Evidence links
```

### 阶段 C：至少两个比赛复现同类问题，再提取 common skills

建议满足下面任一条件才升为 common skill candidate：

```text
- 两个以上比赛都出现同样模式
- 一个比赛出现严重事故，且可通过通用 guardrail 避免
- 某个流程反复消耗大量 token / 人工时间
- 某个流程显著提升 CV/LB/迭代速度
- 某个失败可写成 regression test
```

比如：

```text
common skill:
  "summarize-long-tracking-issue"
  来自：nemo + orbit 都出现 long issue token heavy 问题

common skill:
  "validate-submission-before-gate"
  来自：多个 Kaggle 比赛都需要检查 submission shape / columns / row count

common skill:
  "cv-lb-gap-analysis"
  来自：Nemo/Spaceship/表格赛都需要解释 CV 与 LB 不一致

common skill:
  "environment-agent-arena-evaluation"
  来自：Orbit 这类 multi-agent ladder 比赛需要本地 arena、paired seeds、rating noise 分析
```

### 阶段 D：common insight 不能直接变成 KCA core，必须走 promotion gate

KCA 的 M7 架构已经把 **Command / Skill / Tool / Job** 分层了：Command 是确定性 CLI/API；Skill 是 `.kca/skills/<name>/SKILL.md` 下的 agent workflow recipe；Tool 是有 schema、timeout、permission、sandbox、audit 的可执行动作；Job 是带 budget、turn、cost、runtime 和 decision gates 的 durable record。

所以 promotion 应该这样分流：

```text
只是经验：
  docs/kca/insights/*.md
  competitions/_shared/insights.md

可复用工作流：
  .kca/skills/<skill-name>/SKILL.md

需要确定性执行：
  tools/kca/... 或 kca CLI command

需要安全边界：
  .kca/permissions/*.yaml / permission policy

需要长期防回归：
  tests/ 或 eval benchmark

只是某比赛特例：
  competitions/<slug>/insights.md，不升入 KCA
```

尤其注意：KCA runtime agents 本来就要求 competition-specific policy、sandboxing、budget limits、approval gates 和 audit logging。 所以任何“自动升级 KCA 能力”的动作，都应该通过 issue/PR/test，而不是让比赛 agent 自己读到一个 insight 后直接改 core。

## 2. 需要注意哪些问题？

最重要的是防止 **过度泛化** 和 **证据污染**。

### 2.1 区分事实、假设、策略、规则

每条 insight 建议带标签：

```yaml
type: fact | hypothesis | tactic | bug | rule | anti-pattern
confidence: low | medium | high
evidence:
  - competition:
    run_id:
    submission_id:
    issue:
    file:
transfer_scope:
  applies_to:
  not_applies_to:
status: candidate | proposed | accepted | implemented | validated | deprecated
```

例如：

```yaml
insight_id: INS-2026-06-13-001
title: Long tracking issues become token-heavy; compact competition docs work better
type: anti-pattern
confidence: high
evidence:
  - competition: nemo
    source: issue #...
  - competition: orbit
    source: issue #...
transfer_scope:
  applies_to:
    - active Kaggle competition management
    - Claude Code long-running tasks
  not_applies_to:
    - one-off bugfix
proposed_kca_change:
  kind: skill
  name: consolidate-competition-context
```

### 2.2 不要把 LB 噪声当成真理

特别是 Orbit 这类 ladder / multi-agent 环境，单次 LB 或短期 rating 波动很容易误导。common skill 提取时应该优先看：

```text
- 本地 paired-seed A/B
- 多次 run 的稳定性
- 失败复现率
- 是否节省 token/人工时间
- 是否减少事故
```

而不是“某次 public score 上去了，所以这个策略应该进 KCA”。

### 2.3 明确 human approval 边界

项目规则已经明确：Kaggle submissions、kernel pushes、dataset uploads 和其他 remote side effects 需要人工批准；任务 prompt 要有 acceptance criteria 和 stop condition；worker loop 要有 budget、turn、time、side-effect limits；外部提交前要先跑 tests/local validation。

所以 insight miner 可以自动读、总结、提出 candidate，但不能自动：

```text
- kaggle submit
- kernel push
- dataset upload
- merge PR
- 改 permission policy 让危险动作默认 allow
- 读取 .env / kaggle.json / secrets
```

### 2.4 不要让 summary 成为第二事实源

`competitions/<slug>/README.md` 应该是压缩入口，不是唯一事实源。原始 issue/comment/worklog 可以归档或链接，重要证据要保留链接。否则以后 KCA 分析“为什么成功/失败”时，会基于二手总结不断漂移。

## 3. Orbit 放 `competitions/`，Nemo 放 `experiements/` 的差异从何而来？

我猜这个差异不是深层设计，而是 Claude Code 根据上下文做了不同推断：

```text
Orbit:
  被理解成一个独立 Kaggle competition
  有规则、agent、submission、leaderboard、比赛目录
  → 放到 competitions/orbit/

Nemo:
  可能被理解成一个 experiment、模型路线、notebook 尝试或 NeMo 方案
  而不是独立比赛
  → 放到 experiments/ 或误拼的 experiements/
```

按照你的目标，我建议统一采用这个概念模型：

```text
Competition:
  一个外部比赛/挑战本体
  有 slug、rules、data、metric、deadline、leaderboard、submission channel

Experiment:
  某个 competition 下面的一次假设/路线/版本
  有 config、run、CV、artifacts、submission 结果

Run:
  某个 experiment 的一次执行

Submission:
  某个 run 产出的外部提交或 kernel push
```

这和 KCA 的 M2/M4 设计是吻合的：M2 控制平面已经包含 projects、competitions、sessions、jobs、tasks，以及 messages/discussions/research notes、experiments/runs/metrics/artifacts/submissions 等对象。 M4 也明确 planned capabilities 包括 competition metadata/rule notes、data checksum、baseline notebook/script、CV、experiment tracking、leaderboard result、submission format validation、kernel push 和 Kaggle submit approval。

所以我的建议是：

### 如果 Nemo 是一个独立 Kaggle 比赛

放这里：

```text
competitions/nemo/
```

内部再放：

```text
competitions/nemo/experiments/<experiment-name>/
```

### 如果 Nemo 是某个比赛里的模型/方案/实验路线

例如它其实是某个 competition 的 NeMo/LLM/LoRA 方案，那应该放：

```text
competitions/<actual-competition>/experiments/nemo-<variant>/
```

而不是 root-level `experiments/`。

### root-level `experiments/` 应该只用于 KCA 平台自身实验

例如：

```text
experiments/
  agent-loop-prompting/
  model-routing/
  eval-harness/
  ui-prototype/
  local-llm-summarizer/
```

它们不是 Kaggle 比赛本体，而是 KCA 产品/平台实验。

另外，`experiements/` 是拼写错误，建议尽快 `git mv` 到正确位置，避免 agent 后面继续把错误路径当成惯例。
