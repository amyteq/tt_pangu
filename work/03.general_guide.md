# Q1:
最近在使用claude code时发现token使用的比之前快,最近一个是切换模型,切换到了Fable5,Effort调到最大max,还有就是开启了auto mode。第三个改变就是有两个任务使用了long running issues,并且让claude code经常读取issues里的comments,follow up,并且update in place或者inline。不知道上面三个改变哪个对token使用增加贡献最大,请比较分析,谢谢。

# A1:
我的判断：**最大贡献很可能是 “Fable 5 + effort=max” 和 “long-running issues 反复读 comment/follow-up/update” 的叠加；auto mode 通常不是第一大直接 token 消耗源，但它会放大另外两项。**

如果按“最可能导致你明显感觉 token 用得更快”排序，我会这样排：

```text
1. Fable 5 + effort=max
   直接放大每一步的 thinking/output token，并且 Fable 5 本身更贵。

2. Long-running issue workflow 反复读取 comments / follow-up / inline update
   直接放大上下文输入 token；随着 issue/comment 变长，每一轮都更贵。

3. Auto mode
   直接开销通常较小；主要是因为少了 permission 停顿，Claude 能连续执行更多 tool calls 和更多轮。
```

但如果你的两个 long-running issues 很长、每次都让 Claude 读完整 issue + 全部 comments，那么第 2 项在**总 token 数量**上可能超过第 1 项；如果你主要看的是**费用/usage credit burn rate**，第 1 项通常更明显。

---

## 1. Fable 5 + effort=max：最大“单步成本放大器”

这个变化非常大。

Fable 5 的 API 价格是 **$10 / MTok input、$50 / MTok output**；Opus 4.8 是 **$5 / MTok input、$25 / MTok output**。也就是说，单看 API pricing，Fable 5 是 Opus 4.8 的 **2 倍 input 和 2 倍 output 单价**。([Claude API Docs][1])

更关键的是 effort。Claude Code 文档明确说，`max` 是最深 reasoning，**“no constraint on token spending”**，并且建议不要广泛默认采用，因为可能 overthinking、收益递减。([Claude Code][2]) Fable 5 又是 always-on adaptive thinking；文档明确说 Fable 5 的 thinking 不能关闭，`MAX_THINKING_TOKENS=0`、session toggle、`alwaysThinkingEnabled` 对它都无效，而且 thinking tokens 即使折叠/隐藏也会计费。([Claude Code][2])

所以如果你从：

```text
Opus 4.8 / high
```

变成：

```text
Fable 5 / max
```

那不是一个小调参，而是同时发生了：

```text
per-token price ↑
thinking/output token ↑
每步更愿意深思考 ↑
cache 因 model/effort change 可能被重建 ↑
```

还有一个容易忽略的点：**切模型和改 effort 会让 prompt cache 失效一次**。Claude Code 文档说切换模型会让下一次请求读取完整 conversation history 且没有 cache hit；effort level 也是 cache key 的一部分，改 `/effort` 后下一次请求也会 miss cache。([Claude Code][3]) 这通常是“一次性变贵”，但如果你在 session 中频繁切模型/effort，就会反复发生。

我的建议：

```text
默认不要用 Fable 5 + max。
```

改成：

```bash
claude --bg --name "task" --model fable --effort high
```

或对普通工程任务：

```bash
claude --bg --name "task" --model opus --effort high
```

只有在这些场景才临时用 `max`：

```text
复杂架构决策
大规模 refactor 方案推演
疑难 bug root cause analysis
高风险 migration 设计
需要一次性深度 reasoning 的 final review
```

更经济的模式是：

```text
plan/reasoning 阶段：Fable high 或 Opus xhigh/max
implementation 阶段：Opus high / Sonnet high
mechanical update / docs cleanup：Sonnet medium/high
```

## 2. Long-running issues + 反复读 comments：最大“累计输入 token 放大器”

这项不一定让**单步**最贵，但很容易让**总量**暴涨。

Claude Code 成本文档说得很直接：**token costs scale with context size**；上下文越大，每条消息处理的 token 越多。文档也建议在切换任务时 `/clear`，因为 stale context 会在后续每条消息里浪费 token。([Claude Code][4])

你的 workflow 里有几个典型 token 放大点：

```text
1. issue body 很长
2. comments 越积越多
3. 每次 follow-up 都重新读全部 comments
4. update in place / inline 要先读原文、再生成修改版
5. long-running issue 同一个 session 不断累积上下文
6. Claude 为了保持一致性，会反复引用之前 discussion / decisions
```

这类问题的特点是：**越跑越贵**。
即使模型和 effort 不变，长 issue 也会让每轮 input token 变大。

更糟糕的是，如果你让 Claude “经常读取 issues 里的 comments, follow up, update in place or inline”，它可能每次都做：

```bash
gh issue view <id> --comments
gh pr view <id> --comments
gh api ...
```

然后把完整 issue/comment dump 拉进上下文。一次可能没事，十几次就很明显。

我的建议是把 issue workflow 改成 **ledger / digest 模式**，不要反复让 Claude 读全量 comments。

例如要求 Claude：

```text
Read the GitHub issue and comments once.
Create/update docs/worklogs/issue-123-context.md with:
- current decision summary
- unresolved questions
- last processed comment URL or timestamp
- action items
After that, do not re-read all comments unless explicitly asked.
On follow-up, only read comments newer than the recorded last processed comment.
```

更好的 prompt：

```text
For this long-running issue, maintain a compact local issue digest.

Rules:
1. Do not paste full issue comments into the conversation unless needed.
2. Summarize issue comments into docs/worklogs/issue-123-digest.md.
3. Track last processed comment URL / timestamp.
4. On each follow-up, read only new comments since the last processed comment.
5. Before editing the issue, show the minimal patch or replacement section.
6. Keep the digest under 200 lines.
```

这样你的长期成本会下降很多。

## 3. Auto mode：通常不是最大直接 token 源，但会放大执行量

Auto mode 的直接机制是：Claude Code 把 tool calls 送到 classifier 判断，挡住不可逆、破坏性或越界操作；显式 deny/ask rules 会先于 classifier 生效。([Claude Code][5]) 官方错误文档也说明，auto mode 的 classifier 可能因为 transcript 超过上下文窗口而无法判断，这说明它确实会看会话上下文来做安全判断。([Claude Code][6])

所以 auto mode 本身可能带来一些额外请求/分类开销，但我不认为它通常是最大头。它更大的影响是**行为层面**：

```text
default / ask mode:
  Claude 经常停下来等你批准。
  你会自然中断、检查、收敛任务。

auto mode:
  Claude 可以连续读文件、改文件、跑命令、读 issue、更新 comment。
  一个 /goal 可以跑更远、更久。
  tool calls 数量和模型轮数都上升。
```

也就是说 auto mode 的主要作用是：

```text
减少人为刹车 → 增加连续执行轮数 → 间接增加 token
```

如果你的 auto mode 同时配合：

```text
Fable 5 + effort=max
long-running issue
大量 gh issue/pr comment reading
```

那它就是加速器。

我的建议：auto mode 可以保留，但要加边界：

```text
最多处理 N 个 comments
最多读 N 个 files
每 20 turns 总结并停下
不要 update issue body，除非先给 patch
只 append concise status comment，不 inline rewrite 长正文
```

启动时可以这样：

```bash
claude --bg \
  --name "issue-123" \
  --model opus \
  --effort high \
  --permission-mode auto \
  "/goal Work on issue #123. Maintain a compact digest. Stop after 30 turns or when you need human decision."
```

| 改变                          | 影响类型                      | 对 token/cost 的典型影响 | 我的判断                     |
| --------------------------- | ------------------------- | -----------------: | ------------------------ |

## 如何验证哪个贡献最大

用 `/usage` 建一个小 baseline。Claude Code 文档说 `/usage` 会显示当前 session 的详细 token usage，Pro/Max/Team/Enterprise 还会显示 plan usage bars 和 breakdown；这些数据来自本地 session history，近似但足够做对比。([Claude Code][4])

建议你做 4 组对比，每组做同类型任务 15–20 分钟：

### A. 模型/effort 测试

```text
Session A1: Fable 5 + max
Session A2: Fable 5 + high
Session A3: Opus 4.8 + high
Session A4: Sonnet 4.6 + high
```

同一个 prompt，同一个 repo state，不要混用 session。

看：

```text
input tokens
output tokens
thinking/output ratio
turn count
tool call count
wall time
```

### B. Issue context 测试

同一个模型/effort，例如 Opus high：

```text
B1: 每次读取完整 issue + all comments
B2: 第一次读完整，之后只读 digest + new comments
```

如果 B1 明显贵，说明 long-running issue workflow 是主要问题。

### C. Auto mode 测试

同一个模型/effort，同一个 prompt：

```text
C1: permission-mode default
C2: permission-mode auto
```

观察重点不是单轮 token，而是：

```text
Claude 实际跑了多少轮？
读了多少文件？
跑了多少命令？
是否反复 gh issue view/comments？
```

### D. Cache invalidation 测试

在长 session 里执行：

```text
/model ...
/effort ...
```

然后马上看下一轮 `/usage` 增量。Claude Code prompt cache 文档明确说切模型/改 effort 后下一次请求会完整读 history 且没有 cache hit。([Claude Code][3])


## 我的最终判断

你这次 token 变快，最可能不是单一因素，而是这个组合：

```text
Fable 5 + effort=max
  让每一步更贵、更深 thinking。

Auto mode
  让 Claude 不停下来，连续执行更多轮。

Long-running issue comments
  让每一轮输入上下文越来越大。
```

如果只选一个“最大直接原因”：

```text
Fable 5 + effort=max
```

如果只选一个“最大累计原因”：

```text
long-running issue 反复读全量 comments / follow-up
```

如果只选一个“为什么突然感觉跑得更快、更失控”的原因：

```text
auto mode 去掉了人工刹车
```

我建议你先把默认改回：

```text
Fable 5: high，不用 max
auto mode: 保留，但加 turn/comment/file limits
long-running issue: 改 digest 模式
```

通常这三条就能把 token burn 明显压下来，同时不牺牲太多产出质量。

你的流程整体是合理的，尤其是这几条非常好：

* **计划 / 设计 PR 和实现 PR 分离**；
* **Plan 阶段用 Fable high，Implementation 用 Opus high + auto mode，E2E 用 Sonnet high**；

## 1. 推荐的模型 / 模式矩阵

| 场景                                        |              推荐模型 |        Effort |                        Permission | 说明                           |
| ----------------------------------------- | ----------------: | ------------: | --------------------------------: | ---------------------------- |
| Epic / architecture / stories / test plan |           `fable` |        `high` |                `default` 或 `plan` | 高质量规划，少改代码，主要产出 Markdown     |
| Plan PR comments address                  |           `fable` |        `high` |                         `default` | 同一 session 可保留上下文，但只改 docs   |
| Story implementation                      |            `opus` |        `high` |                            `auto` | 主要 coding loop               |

| Implementation PR comments address        |            `opus` |        `high` |                            `auto` | 读取 digest + PR comments，逐条处理 |
| E2E / acceptance validation               |          `sonnet` |        `high` |                `auto` 或 `default` | 不做大改动，主要验证、提 issue           |

## 4. Plan PR comments address prompt

## 16. Auto mode 配置建议

保留 auto mode，但不要移除默认 deny/soft/hard deny。Claude 官方 auto-mode docs 明确提醒，如果你配置 `allow`、`soft_deny`、`hard_deny` 时不包含 `"$defaults"`，会替换掉默认列表，可能丢掉 force push、`curl | bash`、production deploy、data exfiltration 等内置 block rules。([Claude Code][4])

建议：

```json
{
  "autoMode": {
    "environment": {
      "$defaults": true,
      "source_control": [
        "github.com/amyteq/tt_pangu"
      ],
      "domains": [
        "github.com",
        "api.github.com",
        "supabase.co",
        "*.supabase.co"
      ]
    },
    "allow": [
      "$defaults"
    ],
    "soft_deny": [
      "$defaults",
      "production Supabase migrations require human manual apply",
      "Kaggle submissions require human approval"
    ],
    "hard_deny": [
      "$defaults",
      "Never read .env, kaggle.json, SSH keys, cloud credentials, or GitHub PATs",
      "Never force push",
      "Never run sudo",
      "Never perform destructive production operations"
    ]
  }
}
```

然后检查：

```bash
claude auto-mode config
claude auto-mode critique
```

官方文档也建议用 `claude auto-mode defaults/config/critique` 检查有效规则。([Claude Code][4])

## 17. Token 和准确率控制规则

为了提高 agent 准确率和效率，我建议固定以下规则：

### 17.1 不要让 issue/PR comments 成为上下文黑洞

```text
Full comments → digest → delta only
```

不要反复：

```bash
gh pr view 123 --comments
gh issue view 456 --comments
```

而是：

```text
1. 第一次读全量
2. 写 docs/reviews/PR-123-review-digest.md
3. 后续只读 digest + new comments
```

### 17.2 不在一个 session 里混多个阶段

```text
Plan session:
  只做 epic/stories/test plan/ADR。

Implementation session:
  只做 story execution。

E2E session:
  只验证和提 issue。
```

### 17.3 不频繁切模型 / effort

模型切换和 effort level 改变会触发下一次请求 cache miss。Claude Code prompt caching 文档明确把 switching models 和 changing effort level 列为会 invalidates cache 的动作。([Claude Code][3])

### 17.4 每个 task 都有 stop condition

你已有 practice 也强调每个任务 prompt 必须带停止条件。

### 17.5 使用 subagent 处理“会污染主上下文”的 side task

比如：

```text
PR comment summarization
logs summarization
test failure root cause scan
audit report inventory
issue discussion digest
```

这些非常适合 subagent，因为 subagent 自己读大量内容，主 session 只接收 summary。官方文档也正是这样推荐 subagents：side task 会 flood main conversation 时使用 subagent。([Claude Code][5])

# A3:
## 1. 先澄清：`subagent` 不是 `claude --bg` session

不是。你理解里的：

```bash
claude --bg ...
claude agents --cwd "$PWD"
```

启动的是 **background session / background agent session**。它是一个完整 Claude Code conversation，会显示在 **agent view** 里，每一行都是一个独立 session。官方文档说 `claude agents` 打开的是 background sessions 管理视图；每个 background session 都是完整 Claude Code conversation，可以脱离 terminal 继续运行。([Claude Code][1])

**subagent** 是另一类东西：它是在一个 Claude Code session 内部被 Claude 委派出去的专门 worker。它有自己的独立 context window、system prompt、tools、permissions、model，用来处理高噪音或专门任务，比如搜索代码、总结 PR comments、跑测试并只返回摘要。官方文档明确说，subagents “work within a single session”；如果要运行很多独立 sessions 并从一个界面监控，那才是 background agents / agent view。([Claude Code][2])

所以区别是：

| 概念                     | 怎么创建                                             | 在哪里看到                                                         | 作用                            |
| ---------------------- | ------------------------------------------------ | ------------------------------------------------------------- | ----------------------------- |
| **Background session** | `claude --bg ...`、`/bg`、`claude agents` dispatch | `claude agents` agent view                                    | 一个完整长期 Claude Code session    |
| **Subagent**           | `/agents` 创建，或 `.claude/agents/*.md`，或 `--agent` | 当前 session 的 `/agents` Running/Library；不会作为 agent view row 显示 | 当前 session 内部的专门 worker       |
| **Skill**              | `.claude/skills/<name>/SKILL.md`                 | 通过 `/skill-name` 调用，或 Claude 自动调用                             | 可复用 prompt/workflow/checklist |

Claude Code 里确实没有 `/sub-agent` 这个 skill。管理 subagents 的命令是：

```text
/agents
```

官方文档写的是：运行 `/agents` 打开 subagents interface，可以创建、查看、编辑 custom subagents；也可以直接把 agent 文件放在 `.claude/agents/` 或 `~/.claude/agents/`。([Claude Code][2])

你可以显式调用 subagent 的方式有三种：

```text
1. 自然语言：
   Use the issue-triage-agent subagent to triage issue #123.

2. @ mention：
   @agent-issue-triage-agent triage issue #123.

3. 整个 session 直接使用某个 agent：
   claude --agent issue-triage-agent
```

官方文档说明，subagent 可以通过自然语言、`@` mention，或者 `claude --agent <name>` 作为整个 session 的主 agent 使用。([Claude Code][2])

实践上我建议：

```text
需要长期执行 / 独立 worktree / 独立 PR：
  用 claude --bg / agent view。

需要当前 session 内部做高噪音、一次性、可摘要的工作：
  用 subagent。

需要固化一套可重复流程：
  用 skill。
```

````md
description: Read-only auditor that scans docs, code, tests, workflows, schemas, and inventories for drift. Produces evidence-backed findings and issue drafts. Must not silently change implementation code.

You are the Inventory Drift Auditor.

Your job is to find inconsistencies between docs, code, tests, workflows, migrations, and current project state.

## Responsibilities

1. Build an inventory of relevant files.
2. Compare docs against implementation.
3. Compare milestones/epics/stories against tests and code.
4. Compare workflows against documented engineering practice.
5. Identify stale docs, missing tests, missing closeouts, schema drift, issue drift, and workflow drift.
6. Produce findings with evidence.
7. Convert actionable findings into issue drafts.

## Rules

- Do not edit production code.
- Do not silently fix drift.
- Do not claim drift without evidence.
- Every finding must produce an action:
  - issue draft
  - PR comment
  - doc update proposal
  - ADR proposal
  - test gap
  - explicit no-action record
- Mark uncertain items as `[VERIFY]`.
- Do not read secrets.

## Allowed writes

You may write:

- `docs/reviews/*-drift-audit.md`
- `docs/issues/*-issue-drafts.md`
- `docs/inventory/*`

Do not modify implementation code unless explicitly instructed.

## Output format

```md
# Inventory Drift Audit

## Scope

## Files inspected

## Findings

| ID | Area | Severity | Finding | Evidence | Recommended action |
|---|---|---|---|---|---|

## Issue drafts

## No-action records

## Follow-up recommendations
````

````

典型调用：

```text
@agent-inventory-drift-auditor audit docs/epics, docs/stories, tests, workflows, and migrations for drift after EPIC-012.
````

## 5. Prompt 3：项目当前按 milestone/task 组织，已经跑 14 个 milestones，想转到 epic/story 流程

这个 prompt 要更谨慎，因为它是“组织方式迁移”。重点不是把 14 个 milestones 暴力改名成 epics，而是先做 mapping，再提出 cutover plan。

```text
This project is currently organized around milestones and tasks. It has already completed or partially completed about 14 milestones. We want to transition toward the new development organization discussed in `wiki/01.general_guide.md`:
- feature planning through epics and child stories;
- planning PRs;
- implementation PRs by phase/story;
- PR comment digests;
- story closeout and handoff;
- E2E validation after merge;
- issue triage and issue-to-epic flow;
- Claude Code agents and skills.

Do not rewrite project history. Do not rename or move existing milestone documents destructively. Preserve milestone/task records as historical source of truth.

- PROJECT_STATE.md if present
- docs/milestones.md

- docs/adr/
- .claude/agents/ if present
- .claude/skills/ if present
- .github/workflows/ if present

- list of milestones M0..M14
- status of each milestone
- main deliverables
- existing task docs

Do not move or rename files in this phase.

  - docs/test-cases/

- cutover rules
- compatibility rules for old milestone docs

- Create stories for the workflow transition itself.
- Create a mapping table from old milestones to future epics, not full rewrites.
```

## 6. 我建议你实际落地时的顺序

不要一次性把所有 agents、skills、workflows、docs 都塞进一个巨大 PR。比较稳的切法是：

```text
PR 1:
  workflow guide + terminology + background session/subagent/skill 说明

PR 2:
  agents: implementation-planner, pr-comment-synthesizer, issue-triage-agent

PR 3:
  skills: address-pr-comments, execute-story, story-closeout

PR 4:
  workflows: optional Claude review, PR closeout check, docs quality

PR 5:
  milestone/task → epic/story transition mapping
```

如果你让 Claude Code 自动做，我建议 prompt 里加一个硬限制：

```text
If the change would affect more than 20 files, stop after producing a transition plan and issue drafts. Do not implement the full migration in one PR.
```

这样可以避免 agent 一次性生成一大堆难 review 的文件。
