_Methodology note._ Authored inline by the parent session (Agent / Task
tool not available in this Loop Prompt; same fallback condition documented
in `legacy-archaeologist.md` and `requirements-skeptic.md`). The three
required alternatives (A / B / C) are named verbatim per
`docs/tasks/m12/M12-T001-discovery-debate-gate.md:64–68`. The proposed design
under attack is the default expectation stated in the same task spec:
"Pick one of the three alternatives (default expectation: A — folded enum
— unless the red team's evidence makes B or C decisively better)"
(docs/tasks/m12/M12-T001-discovery-debate-gate.md:78–80).

alternatives:
  1. A. Folded `competition_type` enum on existing `competitions` table — sketch: add `competition_type competition_type_enum NOT NULL DEFAULT 'kaggle'` to `competitions` (supabase/migrations/0004_m4_competition_repo.sql:14–18 is the table being extended); the existing `competition_policy jsonb` (supabase/migrations/0004_m4_competition_repo.sql:18) carries type-specific overrides keyed off the enum; the policy resolver (tools/kca/agent/permission_policy.py:41–51) gains a new arg `competition_type: str` that routes to a per-type `.kca/permissions/<type>-runner.yaml` profile, falling back to the default profile on miss; existing Kaggle rows backfill in one UPDATE; key tradeoff vs proposal: zero-mutation regression for Kaggle rows (the enum default plus untyped jsonb keep ADR-0006 hierarchy intact) at the cost of a permanently jsonb-typed policy surface that can drift over time.
  2. B. Separate `hackathon_competitions` table — sketch: keep `competitions` as the Kaggle-shape table (no schema mutation); add `hackathon_competitions (id, slug, name, deadline, submission_format, team_id, …)` with its own FK out to `teams` + `team_memberships`; the policy resolver fans out on table-of-origin (Kaggle vs hackathon) by inspecting which table the job is bound to; M11 adds a third `ctf_competitions` table later; key tradeoff vs proposal: each table can be normalised to its own type (`deadline timestamptz NOT NULL` on hackathon_competitions, optional on Kaggle) at the cost of a 3× join surface in worker code paths, a duplicated `experiments` / `experiment_runs` FK forest, and a separate set of smoke tests per table.
  3. C. Denormalised `competition_policy` jsonb on `competitions` with no enum — sketch: do not add `competition_type` at all; instead extend `competition_policy` jsonb to carry a `type: 'devpost'` discriminator key alongside the existing `approval_gates: …`; M11 adds `type: 'ctf'` without a migration; the policy resolver does a JSON-path lookup on `competition_policy.type` and routes to the matching profile; backfill is a no-op (existing rows omit `type` → resolver treats as `'kaggle'`); key tradeoff vs proposal: no Postgres ENUM means no migration risk and total flexibility for future types at the cost of giving up DB-level type safety, no `WHERE competition_type='devpost'` index, and no constraint that catches a typo (`'devposst'`) at insert time.

  (M12-T001 task spec invites red team to add ≥1 more if useful; we name
  one supplementary alternative for completeness — it is *not* a
  strawman, and we still recommend the parent session pick from A / B / C.)

  4. D. (Supplementary, non-binding) Hybrid: typed `competition_type` enum + typed `competition_type_policy jsonb` validated by a Postgres CHECK constraint per enum value — sketch: as Alternative A, but augmented with a `CHECK (jsonb_typeof(competition_policy->'approval_gates') = 'object' AND …)` per type; the resolver gets the same type-routing benefit AND the jsonb keys are bounded; key tradeoff vs A: tighter validation at the cost of a more complex migration and per-type CHECK clauses that must be revised every time a new gate is added.

dropped_capabilities:
  - Per-Kaggle-owner secret partitioning (`.env.<owner>` selector) — evidence: tools/legacy/kkr.py:541 (`path = Path(".") / f".env.{owner}"`); survives in: legacy (`tools/legacy/kkr.py` retains it for kkr-replay parity); not preserved by Alternative A, B, or C — this is the canonical Discovery-Debate-Gate failure mode (docs/architecture/discovery-debate-gate.md:18–22), explicitly out of M12 scope but flagged here so a future ADR cannot say "the red team missed it again". Surfaces in legacy-archaeologist §3 (`personas_and_accounts`) and §9 (questions_for_skeptic).
  - Per-competition `competition_policy.approval_gates` key-level type-safety — evidence: supabase/migrations/0004_m4_competition_repo.sql:18 (`competition_policy jsonb NOT NULL DEFAULT '{}'`); survives in: Alternative B (each table can constrain its own jsonb) and Alternative D (CHECK constraint); dropped by Alternative A (the proposal — keys remain untyped) and C (the discriminator is also jsonb).
  - `competition_type='devpost'` index for `WHERE competition_type=…` queries — evidence: supabase/migrations/0004_m4_competition_repo.sql:106–107 (existing `idx_submissions_competition` partial-index pattern); survives in: Alternative A (a B-tree index on the new column is trivial), Alternative B (each table has its own primary scan); dropped by Alternative C (no column means no index, only `WHERE competition_policy->>'type' = 'devpost'` which needs a GIN expression index).
  - The "row owner" persona for the team-scoped rule — evidence: skeptic §personas_and_accounts.4 ("ADR-0018 does not name a 'row owner' column today"; cites tools/kca/competition.py:48 which has no created_by_user_id); survives in: Alternative B if the new `hackathon_competitions` table includes a `created_by_user_id` FK from day one; partially preserved in A (jsonb can carry it but resolver does not enforce); not preserved by C in any structured way.
  - Multi-Devpost-account precedent (the legacy multi-Kaggle-account analog) — evidence: tools/legacy/kkr.yaml:58 vs 66 (`harrysun2006` vs `firefly2006` owner shifts per kernel id); survives in: legacy only — none of A / B / C / D natively support multi-Devpost-account today; ADR-0018 should record this as a known follow-up (M12.x or M13).

long_term_costs:
  cognitive_load:    Alternative A keeps the model "one competitions table, with a type tag" — new contributors read one schema; B forces them to learn N tables and an unwritten join-rule per worker code path; C forces them to know a magic jsonb key they cannot see in `\d competitions`. A wins.
  ops_burden:        At 3am, A breaks like a typo in a permission-profile YAML — readable failure, single-file fix; B breaks like an FK on the wrong table — opaque worker exception, multi-table audit; C breaks like a jsonb-key typo — silent fallback to default profile, the worst kind of failure (no error, wrong behaviour). A wins; C loses badly.
  extensibility:     Next likely scope expansions are (1) **M11 ctf reuse** — A trivially adds `'ctf'` to the existing enum (one `ALTER TYPE … ADD VALUE`), B requires a third table, C requires no migration but no DB-level guard — and (2) **multi-Devpost-account** (legacy multi-Kaggle-account analog from tools/legacy/kkr.py:541) — none of A / B / C structurally solve it, all three require a follow-up ADR; the structural answer (a `competition_credentials` join table) is orthogonal to the type/schema choice. A wins on the named M11 expansion; tie on the multi-account expansion.
  blast_radius:      A's worst-case is "all gates default to ask when a `hackathon-runner.yaml` profile is missing" (skeptic §hidden_constraints.6) — recoverable. B's worst-case is "a Kaggle row leaks into a hackathon query" (a JOIN bug across the two tables) — recoverable but auditable. C's worst-case is "the discriminator key is silently absent from a Devpost row and the resolver routes it through the Kaggle profile, approving a `kaggle_submit` that should have been `devpost_submit`" — credential / leaderboard pollution; this is the same class as the canonical failure mode the Discovery / Debate Gate exists to prevent (docs/meeting-notes/2026-05-24-r3.md §6 referenced from docs/architecture/discovery-debate-gate.md:18–22).

open_disagreements:
  - We do NOT agree that `competition_policy` jsonb (supabase/migrations/0004_m4_competition_repo.sql:18) should remain untyped after M12 ships per-type gates — Alternative A as written leaves keys unbounded; we recommend a **follow-up issue** to add a `CHECK (jsonb_typeof(competition_policy->'approval_gates') = 'object')` or migrate to Alternative D once the M12 gate set stabilises; proposed labels: `area:supabase`, `type:tech-debt`, `priority:P2`. Actionable next step: file the issue at M12-T002 close, cite skeptic §hidden_constraints.6 and §edge_cases.2 as the motivating evidence.
  - We do NOT agree that "all gates default to owner-only for now" (docs/tasks/m12/M12-T001-discovery-debate-gate.md:90) is documentation-sufficient — without a `human_decisions.approved_by_user_id` column (skeptic §personas_and_accounts.6) the rule is unverifiable in audit; we recommend a **spike** in M12-T007 to record approver identity, or an explicit **follow-up issue** if M12-T007 cannot ship it; proposed labels: `area:supabase`, `area:worker`, `priority:P1`. Actionable next step: ask-human at the M12-T007 reviewer-gate design step whether `approved_by_user_id` is in or out.
  - We do NOT agree that `'devpost'` and `'hackathon_devpost'` should both be enum values from M12 (docs/tasks/m12/M12-T001-discovery-debate-gate.md:81) without an explicit "what's the difference" rule — skeptic §explicit_unknowns names this; we recommend the ADR-0018 body either (a) define the boundary verbatim (one sentence; e.g. "`'devpost'` = the Devpost platform, `'hackathon_devpost'` = a Devpost-hosted event that follows the hackathon-format submission shape: README + demo + source; non-hackathon Devpost listings get `'devpost'`") or (b) drop `'hackathon_devpost'` until a real case forces it. Actionable next step: ask-human, then encode the chosen rule in ADR-0018 §Consequences.
  - We do NOT agree that the policy resolver should *silently* fall back to the `default` profile when a type-specific profile is missing (skeptic §hidden_constraints.6) — the canonical failure mode is "silent fallback gives wrong gate"; we recommend the resolver **log a structured warning** (`tool=policy_resolver`, `event=profile_fallback`, `from=<type>`, `to=default`) on every fallback so the audit log records when the type-specific profile was missing. Actionable next step: file as **follow-up issue** for M12-T002 to add the log line; proposed labels: `area:worker`, `type:bug`, `priority:P1`. Cite tools/kca/agent/permission_policy.py:50–51 as the surface to instrument.
  - We do NOT agree that the M11 `'ctf'` reuse is risk-free if M12 ships the enum value but no profile (docs/tasks/m12/M12-T001-discovery-debate-gate.md:82–83) — an out-of-band experiment can insert a `ctf` row, and the resolver will fall back to `default.yaml`, which has no `ctf_*` op entries (.kca/permissions/default.yaml:1–43) — meaning every CTF op resolves to `_tool_default_decision(operation)` = `"ask"` for unknowns (acceptable) BUT a knowing-bad change to a profile could allow it; we recommend a **follow-up issue** for M11 to ship `ctf-runner.yaml` alongside the first CTF code path; proposed labels: `area:policy`, `area:worker`, `milestone:M11`. Actionable next step: cross-link the follow-up issue from the M12 closing issue when ADR-0018 lands.
