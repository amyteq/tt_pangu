## 第一轮已经确定下来的设计决策

**1. Core worker 用 Claude Agent SDK，不只是 Claude Code CLI。**
CLI 用来 dogfood、调 prompt、调 skill、调 hook；SDK 用来做你产品里的长期 agent worker。

**2. Supabase 是 control plane。**
它记录 session、job、message、research、experiment、run、submission、artifact、human decision、agent event。代码和大文件不要塞数据库；代码进 git，artifact 进 storage。

**3. 每个比赛任务都应该是可审计 loop。**
不是“agent 自己一直写代码”，而是：

```text
需求 / idea
→ research
→ plan
→ implement
→ test / evaluate
→ analyze result
→ decide next iteration
→ maybe prepare submission
→ human approval
→ submit / commit / continue
```

**4. Kaggle 和 CTF 要分开 policy。**
Kaggle 关注规则、metric、CV、submission limit、leaderboard overfitting。CTF 只允许明确授权的 challenge/local lab/sandbox，不做真实世界攻击、外部扫描、凭证窃取或持久化。

**5. Hooks 必须从第一天就加。**
Claude Code hooks 可以在 tool use 前后运行，用来 block 危险操作、记录审计、要求 human approval；官方也把 hooks 作为自动 lint/test、拦截危险操作、权限控制和生命周期管理的重要机制。([Claude][7])

## 1. Claude Console / Claude Code / Team：你的理解需要修正一下

你说的“Console 支持 team，但需要单独购买 credits；Code 只能个人使用，无法 invite team members”——**现在不完全对**。

更准确的拆分是：

| 概念                            | 用途                                                  | Team/协作                               | 计费                                |
| ----------------------------- | --------------------------------------------------- | ------------------------------------- | --------------------------------- |
| **Claude Console / Platform** | API、Workbench、API keys、workspaces、spend/rate limits | 支持 organization / workspace / members | API 用量计费 / credits / spend limits |
| **Claude Web/Desktop/Chat**   | 人类交互使用 Claude                                       | Pro/Max/Team/Enterprise               | 订阅或企业计费                           |
| **Claude Code**               | Terminal / IDE / Desktop / Web coding agent         | 不是只能个人用；Team/Enterprise 也可用           | 可走订阅 seat，也可走 Console/API 用量      |

Claude API 的 key 是从 Console 生成的，并且官方建议用 workspaces 来分割 API keys 和按 use case 控制 spend；API 也有 rate limits 和 spend limits。([Claude Platform][1])

Claude Team plan 的 Standard seats 已经包含 Claude Code，Premium seats 则在 Standard 之上给更高 usage；Team plan 需要至少 5 个成员，且是组织账号，不是个人 Pro/Max 账号的简单升级。([Claude Help Center][2])

Enterprise 也包含 Claude Code，但当前 Enterprise 文档特别说明 seat fee 只覆盖访问权限，Claude、Claude Code、Cowork 的 token usage 会按 API rate 另行计费。([Claude Help Center][3])

对你的项目来说，最重要的一点是：**开发时人可以用 Claude Code Team/Pro/Max；产品化 worker 不应该依赖个人 claude.ai 登录额度，而应该用 API key / Console workspace。** Anthropic Agent SDK 文档也明确说，除非特别批准，第三方开发者不应把 claude.ai login 或 rate limits 提供给自己的产品，应该用 API key authentication。([Claude API Docs][4])

## 3. “Claude Code / Claude Agent SDK 做核心 worker”到底是什么意思？

## 4. Claude Agent SDK 的写代码能力是不是 SOTA？

要分清楚：**Claude Agent SDK 是 agent harness，不是模型本身。写代码能力 = 模型能力 + agent loop + tools + repo memory + tests + sandbox + eval。**

当前我会这样判断：

**Claude Opus 4.7 / Sonnet 4.6 + Claude Agent SDK 是非常强的默认核心 worker 选择。** Anthropic 官方称 Opus 4.7 是其“most capable model for complex reasoning and agentic coding”，Sonnet 4.6 面向 coding、agents、enterprise workflows。([Claude API Docs][6])

但“绝对 SOTA”要看 benchmark。OpenAI 自己的 GPT-5.5 发布页给了一组对比：在 SWE-Bench Pro Public 上，GPT-5.5 是 58.6%，Claude Opus 4.7 是 64.3%；在 Terminal-Bench 2.0 上，GPT-5.5 是 82.7%，Claude Opus 4.7 是 69.4%。这说明不同 benchmark 下胜负会变，不能简单说某一个模型在所有 coding agent 场景都第一。([OpenAI][7])

对 Kaggle 来说，代码 benchmark 也只是一部分。真正胜负还包括：

```text
比赛规则理解
metric 和 validation 设计
data leakage 防控
实验记录
特征工程 / 推理策略 / fine-tuning
GPU/CPU 预算
public leaderboard overfitting 控制
提交节奏
```

所以我建议：**Claude Agent SDK + Sonnet/Opus 做主 worker，GPT-5.5/Codex 做独立 reviewer 或 alternate solver，local models 做低成本 subagents。**

| **vLLM 本地模型**                      | cheap/private subagents、日志总结、批量 idea、简单代码           | OpenAI-compatible server，能用 OpenAI client 调本地模型                        | 代码能力取决于具体模型；工具调用/长上下文/agent reliability 要自己验证    | **先做辅助，不做主 worker**        |
| **Ollama 本地模型**                    | 本地轻量 subagent、快速实验                                  | OpenAI compatibility，支持 tool calling                                   | 更适合轻量本地任务；production agent loop 还要自己搭            | **辅助 worker**              |
| **Lovable**                        | 产品壳、dashboard、管理台、MVP UI                            | 很适合快速做 Web UI / Supabase app                                           | 不适合作为底层长期 coding worker                          | **后面接 UI**                 |

vLLM 的 OpenAI-compatible server 可以用官方 OpenAI Python client 通过 `base_url` 调用本地模型；Ollama 也提供 OpenAI compatibility，并支持 tool/function calling。([vLLM][12])

LangGraph 更适合做外层 workflow：它的 durable execution 可以把每一步状态存到 durable store，隔一周也能恢复；它的 human-in-the-loop middleware 可以在模型提出需要审查的 tool call 时暂停并等待人工决策。([LangChain Docs][13])

所以我会这样落地 model router：

```text
task_type = "routine_code"        -> Claude Sonnet
task_type = "hard_debug"          -> Claude Opus
task_type = "independent_review"  -> GPT-5.5 / Codex
task_type = "final_high_value"    -> GPT-5.5 Pro or Opus
task_type = "log_summary"         -> local vLLM/Ollama
task_type = "batch_hypothesis"    -> local / cheap model
```

## 7. Claude Code、ChatGPT Pro 5.5、Lovable、GitHub 如何保证 memory 一致？

最佳实践：**不要相信任何一个工具的隐藏 memory；GitHub repo 是唯一 durable memory。**

Claude Code / Agent SDK 可以读取 `CLAUDE.md`、`.claude/skills/*/SKILL.md` 等项目文件。([Claude API Docs][4]) Codex 明确支持 `AGENTS.md`，会在工作前读取它来获得项目级指导。([OpenAI Developers][14])

所以我建议 repo 里保留这套文件：

```text
CLAUDE.md                         # Claude Code 专用
AGENTS.md                         # ChatGPT/Codex/通用 agent 指令
PROJECT_STATE.md                  # 当前项目状态、下一步、开放问题
docs/adr/*.md                     # 架构决策记录
docs/architecture/*.md            # 架构文档
docs/tooling/*.md                 # 工具协议、脚本约定
docs/testing/*.md                 # 回归测试/比赛用例
docs/meeting-notes/YYYY-MM-DD.md  # 讨论纪要
docs/milestones/_templates/handoff-prompt.md            # 切换 AI 工具时的上下文 prompt
```

每次我们在这里、Claude Code、ChatGPT Pro、Lovable 里做了重要决策，都不要只留在聊天记录里，而是生成一个小 patch：

```text
更新 PROJECT_STATE.md
新增/更新 ADR
更新 AGENTS.md / CLAUDE.md
更新 meeting note
commit 到 GitHub
```

对 ChatGPT Pro / Codex 的使用方式：

```text
上传或粘贴：
- PROJECT_STATE.md
- AGENTS.md
- 相关 ADR
- 当前问题

要求输出：
- decision note
- patch
- reviewer comments
- risk list
```

对 Lovable 的使用方式：

```text
让 Lovable 主要读：
- AGENTS.md
- PROJECT_STATE.md
- Supabase schema
- UI requirements

不要让 Lovable 成为架构 memory 的唯一来源。
```

我已经在补充包里放了 `AGENTS.md`、`PROJECT_STATE.md`、`docs/milestones/_templates/handoff-prompt.md` 和两份 ADR，建议你直接拷进去并 commit。

## 8. 你已有的 Kaggle 辅助脚本怎么整合？

非常适合整合，而且应该尽早整合。不要让 agent “自由猜脚本怎么用”，而是把脚本变成**稳定、可审计、有 side-effect 分类的工具层**。

建议把现有脚本整理成一个 namespace，比如：

```bash
kca notebook to-ipynb path/to/script.py --output path/to/notebook.ipynb
kca notebook to-py path/to/notebook.ipynb --output path/to/script.py
kca kaggle data download --competition <slug> --output data/<slug>
kca kaggle kernel push --kernel-dir kernels/<name> --dry-run
kca kaggle submit --competition <slug> --file submission.csv --message "..."
kca kaggle submissions list --competition <slug>
kca runs record --run-dir runs/<slug>/<run_id>
```

每个工具要标注安全等级：

| 类型             | 例子                                          | 默认策略                   |
| -------------- | ------------------------------------------- | ---------------------- |
| `read-only`    | 查看 submissions、leaderboard、discussion       | 允许                     |
| `local-write`  | 转 notebook、生成 submission.csv、写 metrics.json | 允许，但限制在 repo/workspace |
| `remote-write` | push kernel、上传 dataset、更新 notebook          | 需要 human approval      |
| `submission`   | Kaggle competition submit                   | 必须 human approval      |

Kaggle CLI 官方本身就支持 competitions list/files/download/submit/submissions/leaderboard/topics 等命令，也支持 kernels、datasets、forums、models 等 command groups。([GitHub][15])

第一阶段可以让 Claude Code 通过 Bash 调这些 wrapper，但用 hooks 拦截危险命令。第二阶段再把 wrapper 升级成 Agent SDK custom tools / MCP tools。Agent SDK 本身支持 built-in tools，也支持 custom tools；官方对比里也说明 Agent SDK 的 custom tools 是在进程内 Python/TypeScript functions。([Claude API Docs][4])

我已经在补充包里加了：

```text
docs/tooling/kaggle-tooling-integration.md
.claude/skills/kaggle-tooling-integration/SKILL.md
.claude/skills/kaggle-evaluation-harness/SKILL.md
```

下一步你可以把现有脚本路径列出来，我们把它们映射成正式工具表：

```text
script_path
purpose
input
output
side_effect
approval_required
wrapper_command
test_command
```

## 9. 之前比赛 / 长期 open 练习项目能否做 test case？

**非常适合，而且应该成为平台的 regression suite。**

我建议分 5 层：

```text
Level 0: 工具 smoke test
- python/ipynb 转换
- 运行 tiny script
- 解析 metrics
- 写 run record

Level 1: 经典快速 Kaggle
- Titanic
- House Prices
- Digit Recognizer

Level 2: notebook / kernel workflow
- 构建 notebook
- dry-run push
- human approval gate
- submission format validation

Level 3: reasoning-heavy / LLM-heavy competition
- AI Mathematical Olympiad-style
- NVIDIA Nemotron-style
- 检查 research + eval + long-running experiment tracking

Level 4: authorized CTF sandbox
- 只用本地 challenge 文件或容器
- 记录 commands / writeup
- 阻止外部扫描、凭证窃取、真实目标攻击
```

像 NVIDIA Nemotron 这种比赛尤其适合当 Level 3，因为它不是传统 tabular ML，而是 research、reasoning、训练/微调、分析 dashboard、notebook/submission 流程的综合测试。你给的类似比赛还有一个很好的参考：Nemotron Progress Prize winning submission 的 GitHub repo 本身就包含 `.claude`、`.codex`、训练脚本、metrics 页面、problem grid、corpus/training 分析页面等结构，说明这类比赛非常适合测试“AI coding agent + experiment tracking + analysis UI”的工作流。([GitHub][16])

但真实 Kaggle 提交要当成 external side effect。平台 test case 里应优先做：

```text
local validation
dry-run submission
submission.csv schema check
notebook metadata check
Kaggle command construction check
human approval request generation
```

只有人工批准后才真正执行：

```bash
kaggle competitions submit ...
```
