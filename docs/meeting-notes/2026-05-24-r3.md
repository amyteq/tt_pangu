## 1. Claude Code 能否自动把 session 对话和操作日志记录到项目 `logs/xxx.md`？

**部分支持，但需要你自己用 hooks / export 脚本落地。**

Claude Code 官方会持续保存 session，本地 transcript 默认在：

```text
~/.claude/projects/<project>/<session-id>.jsonl
```

也可以在会话里用 `/export` 把当前 conversation 保存为纯文本文件；官方文档还说明这些本地 session 文件默认 30 天后清理，可通过配置调整。([Claude Code][1])

但是，**Claude Code 默认不会自动把完整对话保存到当前 repo 的 `logs/` 目录**。要做到这一点，推荐用 hooks。Claude Code hooks 能在 `SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PostToolUse`、`Stop`、`SubagentStart/Stop`、`TaskCreated/Completed`、`SessionEnd` 等生命周期事件触发；hook 输入里包含 `session_id`、`cwd`、`transcript_path` 等信息。([Claude Code][2])

你项目里其实已经有一个基础版本：`audit_event.py` 会从 hook stdin 读取 JSON payload，然后写到当前项目的 `.agent/audit/tool-events.jsonl`，字段包括 `timestamp`、`hook_event_name`、`tool_name`、`session_id`、`cwd` 和完整 payload。 这说明你的项目已经具备 **tool-event audit log**，但还没有完整的 **conversation transcript mirror / session summary log**。

我建议分三层做：

```text
.agent/audit/
  tool-events.jsonl              # raw hook events, 默认不提交或只提交 sanitized 样例

logs/claude-sessions/
  <date>-<session-id>.jsonl       # transcript mirror，可选，不建议默认 commit
  <date>-<session-id>.summary.md  # curated session summary，可 review 后 commit

docs/milestones/*/handoff.md
  m9-handoff.md
  m10-handoff.md                  # milestone 级别核心记忆，应该 commit
```

关键安全建议：**不要默认把完整 transcript commit 到 GitHub**。Claude session 里可能包含本地路径、命令输出、错误日志、环境变量片段、PR 链接、甚至误打印的 secret。更好的做法是：

```text
raw logs:
  .agent/audit/**
  logs/claude-sessions/raw/**
  默认 .gitignore

curated memory:
  PROJECT_STATE.md
  docs/milestones/*/handoff.md*.md
  docs/adr/*.md
  docs/meeting-notes/*.md
  docs/evidence/*.md
  review 后 commit
```

可以让 Claude Code 加一个 skill：

```text
.claude/skills/session-closeout/SKILL.md
```

用途是每次长任务结束后生成：

```text
- What changed
- Files changed
- Tests run
- Decisions made
- Open questions
- Follow-up issues to create
- Memory updates proposed
```

然后由 human 批准后更新 `PROJECT_STATE.md`、`docs/milestones/*/handoff.md`、ADR 或 GitHub issue。

## 2. Claude Code 支持 GitHub webhook 吗？能否响应 PR review / comments / labels？

**支持几种不同层级，但要区分 “GitHub Actions 触发新 agent run” 和 “push 事件进入正在运行的本地 session”。**

### 方案 A：GitHub Actions + `@claude`，最稳

你现在已经有 `.github/workflows/claude.yml`，它监听：

```yaml
issue_comment:
  types: [created]
pull_request_review_comment:
  types: [created]
issues:
  types: [opened, assigned]
pull_request_review:
  types: [submitted]
```

并且只有 comment / issue / review body 包含 `@claude` 时才运行 Claude Code Action。 官方文档也确认 Claude Code GitHub Actions 可以通过 PR/issue 中的 `@claude` 触发，分析代码、创建 PR、实现功能和修 bug，并且 action 是基于 Claude Agent SDK 构建的。([Claude Code][3])

这适合：

```text
@claude review this PR
@claude implement issue #123
@claude summarize unresolved review comments
@claude update docs based on this decision
```

如果你想让它更新 issue comments / labels / PR comments，workflow 权限需要从 read 扩到 write，例如：

```yaml
permissions:
  contents: write
  pull-requests: write
  issues: write
  actions: read
  id-token: write
```

但我建议分 workflow：

```text
claude.yml
  手动 @claude 响应，允许 contents/pull-requests/issues write

claude-code-review.yml
  自动 PR review，默认只读或只写 review comment

issue-triage.yml
  label/comment triage，issues: write，但不改代码

labels-sync.yml
  只同步 .github/labels.yml，需要人工 workflow_dispatch
```

工程实践文档里的 AI pickup rule 很适合这里：implementation agent 只能处理 open issue、带 `ai:ready`、决策已 `decision:confirmed`、有 acceptance criteria、无 `ai:blocked`，且不涉及 secrets/破坏性 migration/生产 infra/客户可见副作用，除非 human 明确批准。

### 方案 B：Claude Code Routines + GitHub trigger，云端事件触发

Claude Code Routines 支持 schedule、API trigger、GitHub event trigger，运行在 Anthropic-managed cloud infrastructure；GitHub trigger 会在匹配事件发生时启动一个新 session。([Claude Code][4]) 官方文档说明 GitHub triggers 当前支持 PR 和 release 两类事件，PR 事件包括 opened、closed、assigned、labeled、synchronized 等；每个匹配事件都会启动独立 session，不复用之前的 session。([Claude Code][4])

这适合：

```text
PR labeled ai:ready → 新 cloud session 生成 plan
PR updated → 自动 review diff
release created → 生成 release notes / readiness report
nightly → issue backlog grooming
```

但它不适合保存“一个长期本地 session 的连续上下文”，因为每个 GitHub event 是新 session。你的 repo memory 仍然要靠 GitHub 文件和 issue/PR 记录。

### 方案 C：Claude Code Channels，把 webhook 推进正在运行的本地 session

Claude Code Channels 是另一类东西：它允许 MCP server 把 messages、alerts、webhooks 推入一个正在运行的 Claude Code session。官方说它可用于 CI results、chat messages、monitoring events，让 Claude 在你离开终端时也能反应；这是 research preview，需要 Claude Code v2.1.80+，并且 session 启动时要用 `--channels` opt-in。([Claude Code][5]) Channels reference 说明 channel 本质是 MCP server，通过 `notifications/claude/channel` 把外部事件送进 Claude Code session，可做 one-way webhook 或 two-way chat bridge。([Claude Code][6])

这适合：

```text
GitHub webhook → local channel server → active Arch Claude session
CI failed → Claude sees event immediately
Issue label changed → Claude receives payload
PR review submitted → Claude receives payload and responds
```

但它更复杂，且是 research preview。我建议你的路线是：

```text
短期：
  GitHub Actions @claude + issue labels/comments

中期：
  Routines 处理 cloud-side GitHub event automation

高级：
  Channels 将 selected GitHub webhook 推入正在运行的 Arch session
```

## 3. 如何从 GitHub comments 中提取需求确认/设计变更并沉淀为核心记忆？

这件事不能让 Claude “看到评论就直接改 PROJECT_STATE”。应该用 **两阶段 memory promotion**：

```text
GitHub comment/review/label event
  ↓
Issue Triage / Decision Extractor agent
  ↓
生成 proposed memory patch
  ↓
human review
  ↓
更新核心记忆文件
```

我建议新增这些文件：

```text
.claude/agents/github-decision-extractor.md
.claude/agents/github-issue-triage.md
.claude/agents/pr-review-followup.md

.claude/skills/github-comment-distill/SKILL.md
.claude/skills/memory-promotion/SKILL.md
.claude/skills/pr-closeout-review/SKILL.md
```

`github-comment-distill` 的职责：

```text
输入：
  issue/PR comments, review comments, labels, PR diff, linked task doc

输出：
  confirmed_requirements:
  changed_requirements:
  confirmed_design_decisions:
  changed_design_decisions:
  open_questions:
  blockers:
  proposed_labels:
  proposed_core_memory_patch:
```

`memory-promotion` 的职责：

```text
只生成 patch，不直接 claim truth：
- PROJECT_STATE.md patch
- docs/adr/xxxx.md draft
- docs/tasks/Mx-Txxx.md update
- docs/milestones/mx/handoff.md update
- GitHub issue comment summary
```

沉淀规则建议：

```text
comment 只是 evidence，不自动成为 truth
label decision:confirmed + human 明确 wording 才能进入 ADR / PROJECT_STATE
模糊评论 → decision:needed + ai:blocked
实现细节 → task doc / PR closeout
长期架构决策 → ADR
milestone 状态 → PROJECT_STATE / docs/milestones/README.md
```

这和你的工程实践文档一致：Issue Triage Agent 可以读 comments 并识别问题是否已解决，但不能从模糊评论推断决策；Implementation Agent 只能在确认后的 issue 上工作。

## 4. agents/skills 如何迁移到别的项目？

**不要直接无脑复制到目标项目根目录。最佳方式是“staging → audit → adapt → install”。**

Claude Code skills 是文件系统 artifact，项目级 skills 放在：

```text
.claude/skills/<skill-name>/SKILL.md
```

个人级 skills 放在：

```text
~/.claude/skills/<skill-name>/SKILL.md
```

官方文档说明 project skills 只对当前项目生效，personal skills 对所有项目生效，plugin skills 通过 plugin namespace 生效；skills 的 body 只在使用时加载，适合把重复流程从 `CLAUDE.md` 中拆出来。([Claude Code][7]) Agent SDK 也支持从 `.claude/skills/`、`~/.claude/skills/` 或 plugin 路径发现 filesystem skills。([Claude Code][8])

我建议采用四层复用模型：

### A. 通用、无项目耦合：做成 personal skill 或内部 plugin

例如：

```text
pr-closeout-review
github-comment-distill
session-closeout
ci-failure-triage
test-coverage-review
```

可以放：

```text
~/.claude/skills/
```

或建立一个内部 repo：

```text
kca-agent-pack/
  skills/
  agents/
  hooks/
  templates/
  README.md
```

然后每个项目通过 submodule/subtree 或脚本安装。

### B. 项目相关但可复用：先放 staging

目标项目里先放：

```text
.agent-import-staging/kca-agent-pack/
```

然后让 Claude Code 执行：

```text
Analyze .agent-import-staging/kca-agent-pack.
For each skill/agent:
- classify as reusable / needs adaptation / reject
- identify project-specific assumptions
- identify commands, paths, labels, policies to rewrite
- propose final installation path
Do not install until plan is approved.
```

再迁移到：

```text
.claude/skills/
.claude/agents/
docs/agent-practices/
```

### C. 强项目耦合：不要迁移，只迁移理念

例如 KCA 专用的 Kaggle approval、competition artifact layout、Supabase schema agent，不适合直接复制到普通 SaaS 项目。应该抽象出：

```text
approval-gate-review
artifact-ledger
remote-side-effect-policy
```

### D. 带脚本的 skills：必须安全审计

官方 Agent Skills 文档提醒，Skills 可以包含指令和代码，恶意 Skill 可能诱导 Claude 执行不符合预期的工具或代码，所以只应使用可信来源的 skills。([Claude Platform][9]) 所以迁移时要检查：

```text
- 是否调用 curl/wget/bash remote code
- 是否读取 .env / ssh / cloud credentials
- 是否 git push / deploy / delete
- 是否写绝对路径
- 是否假设某个 repo layout
- 是否修改 permissions/hooks
```

## 5. 产品 release 后是否还依赖 Claude Code？agents/skills/commands 底层调用什么？

**KCA 产品 release 后不应该依赖 Claude Code CLI/desktop 本身。** Claude Code 是开发工具；KCA runtime 应该是你自己的 platform worker。

你现在项目文档已经把两类 agent 区分得很清楚：Claude Code/VS Code/Desktop/Web 是 platform-development coding agents；runtime competition code agents 是平台内部启动的 agent，初始方向是 Claude Agent SDK、隔离 workspace/container、Kaggle Python/notebook-first、未来 model router 支持 Claude、GPT-style、local vLLM/Ollama 等。

更进一步，你当前 M3 里已经把 runtime agent 方向改成了 provider-agnostic：`litellm.completion()` 作为统一 LLM provider interface，Claude、GPT-4o、本地 vLLM/Ollama 可按 job 选择。 这说明 KCA runtime **不是锁死在 Anthropic 模型上**。

不过要分清楚几种能力来源：

```text
Claude Code CLI skills/agents/hooks:
  用于开发 KCA repo；依赖 Claude Code。

KCA .kca/skills or tools:
  你自己定义的产品 runtime skills/tools；不依赖 Claude Code。

Claude Agent SDK:
  可以作为一种 runtime harness，提供 Claude Code-like agent loop、工具执行、context management。

LiteLLM / OpenAI-compatible / vLLM / Ollama:
  可以作为 model provider；你要自己实现 tool loop 或通过 KCA worker adapter 接入。

KCA commands:
  例如 kca run, kca decision, kca kaggle, kca skill；
  release 后就是你的产品 CLI/runtime API，不应该依赖 Claude Code。
```

官方 Claude Agent SDK 的定位是“把 Claude Code 作为 library 构建生产 AI agents”，它提供相同的 tools、agent loop、context management，并且适合 CI/CD、custom applications、production automation。([Claude Code][10]) 但如果你使用 Agent SDK，它主要还是 Claude/Anthropic provider 体系；如果要接 vLLM/Ollama/OpenAI，你需要通过 KCA 的 model router / LiteLLM 路线来承接。

我的建议：

```text
产品 runtime 层：
  KCA Worker API
    - job runner
    - permission policy
    - tool executor
    - audit/event log
    - model router
    - GitHub adapter
    - Kaggle adapter

可插拔 agent backend：
  - Claude Agent SDK backend
  - LiteLLM tool-loop backend
  - OpenAI Responses/Codex backend
  - Local vLLM/Ollama backend
```

这样你可以先用 Claude Agent SDK 获得强 agentic coding 能力，后面逐步替换或混合其他模型。

## 6. 如何让 Claude Code 在 plan/design/architect 阶段更主动发现问题、提问和 debate？

你观察得很对：Claude Code 有时会“按字面完成任务”，不会主动追问隐藏需求。例如你让它接手 `kkr.py/kkr.yaml`，它没有主动发现“多 Kaggle 账户提交”这种重要历史设计理念。其实你的 legacy 工具里已经有不少信号：`kkr.py` 支持 `--env` 覆盖 selected owner 的 dotenv path，`RunManifest` 里有 `owner`、`slug`、`env_path`，`kkr.yaml` 里也出现多个 Kaggle owner/kernel id，例如 `harrysun2006`、`firefly2006`。  

要提高主动性，我建议建立一个 **Discovery / Debate Gate**，不是只靠“plan mode”。

### 做法 1：每个迁移 legacy 的任务先跑 “design archaeology”

新增 skill：

```text
.claude/skills/design-archaeology/SKILL.md
```

要求 Claude 在实现前必须输出：

```text
Legacy design archaeology:
1. What workflows does the legacy tool support?
2. What hidden assumptions exist?
3. What user personas/accounts exist?
4. What side effects exist?
5. What state files/registries exist?
6. What config dimensions exist?
7. Which features should be preserved?
8. Which features should be deprecated?
9. What questions must be asked before implementation?
10. What tests prove behavior parity?
```

对 `kkr.py/kkr.yaml` 这种任务，强制它先识别：

```text
- multi-account / owner / env mapping
- kernel push vs competition submit
- notebook submit vs local file submit
- run registry
- version labels
- fetch/watch/status/list lifecycle
- dry-run behavior
- H100 / docker_image / Kaggle metadata patch notes
```

### 做法 2：在 task template 里加入 “assumption challenge”

每个 architecture task 的 prompt 里固定加：

```text
Before proposing implementation, challenge the task:
- What important requirement might be hidden in legacy files?
- What would break for an expert user?
- What design questions should be asked?
- What should be preserved even if not mentioned?
- What is the minimal reversible implementation?
- Give at least 3 alternative designs and argue tradeoffs.
```

### 做法 3：增加反方 agent

新增 agents：

```text
.claude/agents/requirements-skeptic.md
.claude/agents/legacy-archaeologist.md
.claude/agents/design-red-team.md
```

`requirements-skeptic` 不写代码，只问问题。
`legacy-archaeologist` 只读 legacy scripts/configs，提取设计理念。
`design-red-team` 反驳当前方案，指出丢失能力和长期成本。

### 做法 4：把“询问 human”变成 acceptance criteria

例如：

```text
Acceptance criteria:
- The agent identified at least 5 legacy behavior dimensions.
- The agent listed preserved / changed / dropped behaviors.
- The agent asked human for unresolved design decisions unless all are explicitly answered by docs/tests.
- No implementation starts until hidden assumptions are documented.
```

这比“请主动一点”有效，因为它把主动性变成可检查输出。

## 7. 你现在这些实践之外，还能怎么提高开发效率和准确率？

你已经有一套很强的 workflow：

```text
milestones/tasks + worktrees
Arch Linux Claude Code --bg 长跑
Mac VS Code 做短任务/review
mobile app remote control 批准/回答
GitHub issues/PR/comments/labels 作为第二交互界面
```

我建议补齐下面 12 个实践。

### 1. 给每个 task 增加 “evidence bundle”

每个 PR 必须产出：

```text
docs/evidence/<task-id>/
  closeout.md
  commands-run.txt
  test-results.md
  screenshots-or-traces-index.md
  decisions.md
```

PR body 链接 evidence。工程实践文档也建议 logs 要总结到 issue，并把长期证据放在 `docs/evidence/` 或 GitHub artifact 中。

### 2. 建立 “no silent memory” 机制

每次 Claude Code 结束时强制问：

```text
Does this task change project memory?
- no
- yes: propose patch to PROJECT_STATE.md / ADR / task doc / handoff
```

只有 human approve 后才更新。

### 3. 增加 PR Closeout bot

每个 PR 自动检查：

```text
- linked issue
- acceptance criteria checked
- tests run
- docs updated or not needed
- migrations/RLS/secrets impact
- remote side effects
- evidence link
```

你的 engineering details 里已经建议 `pr-closeout-check.yml` 用于检查 PR body 是否包含 tests/docs/inventory/closeout links。

### 4. 将 “labels” 变成状态机，而不只是标签

建议状态流：

```text
ai:triage
  → decision:needed + ai:blocked
  → decision:confirmed
  → ai:ready
  → ai:implementing
  → PR opened
  → review
  → merged / follow-up issues
```

禁止：

```text
ai:ready + decision:needed
ai:ready + ai:blocked
ai:implementing without owner/branch
```

### 5. 引入 “issue-to-branch naming convention”

例如：

```text
issue #123
branch: claude/issue-123-short-title
worktree: .worktrees/issue-123-short-title
PR title: [#123] Short title
```

这样 GitHub event、Claude session、worktree、logs、evidence 都能对齐。

### 6. 为 Claude Code session 命名

Claude Code 支持命名、resume、branch session；session picker 可以按当前 repo/worktree/branch 查找，并且可以导出 transcript。([Claude Code][1]) 你的长跑命令应统一：

```bash
claude --bg \
  --name "M9-T002-spaceship-baseline-issue-123" \
  ...
```

然后 log/evidence 也用同名 ID。

### 7. 用 Channels 或 Remote Control 做“响应式开发”，但不要替代 GitHub Actions

Remote Control 适合你现在用 mobile app 远程接管本地 session；官方说明 Remote Control 让本地 Claude Code session 继续运行在你的机器上，Web/mobile 只是窗口，适合从手机继续本地任务。([Claude Code][11])

Channels 更适合把外部 webhook 推入本地 session。我的建议：

```text
Remote Control:
  人主动介入、批准、回答问题。

GitHub Actions:
  repo-native 事件、@claude、issue/PR 协作。

Channels:
  高级事件流，例如 CI failed / PR labeled / issue assigned 推入正在跑的 Arch session。
```

### 8. 让 KCA 自己 dogfood GitHub interface

KCA 产品本身未来要能操作 GitHub，所以现在开发 KCA 时就用同一套抽象：

```text
GitHub issue/comment/label event
  → KCA event adapter
  → decision extractor
  → job queue
  → worker/session
  → PR/comment/label update
  → audit log
```

这样你不是“额外做 GitHub automation”，而是在 dogfood 产品核心能力。

### 9. legacy migration 要有 behavior parity tests

对 `kkr.py/kkr.yaml`，不要只迁移代码。要建立：

```text
tests/fixtures/kkr/
  kkr.yaml
  minimal_notebook.ipynb
  fake_kaggle_api.json

tests/test_kkr_parity.py
```

覆盖：

```text
- push --dry-run
- submit --dry-run
- watch/status/list/fetch parsing
- multi-owner env selection
- notebook vs local submit
- version label / registry behavior
```

`kkr.py` 已经有 dry-run、JSON output、本地 registry、watch/status/list/fetch 等能力，适合做 parity suite。

### 10. 对高风险任务使用双 agent review

例如：

```text
Agent A: implement
Agent B: review only
Agent C: test coverage reviewer
Human: final decision
```

工程实践文档本身已经把 Inventory Drift Auditor、Issue Triage Agent、Implementation Planner、Implementation Agent、Milestone Reviewer、Test Coverage Reviewer、Release Readiness Agent 分成不同职责，并规定各自不能越权。

### 11. 给 runtime worker 增加 replay

每个 job 都能：

```bash
kca job replay <job_id> --from-event <n> --dry-run
```

这样当 agent 做错时，你可以复现：

```text
input prompt
model/provider
tools allowed
tool calls
policy decisions
files changed
test results
human decisions
```

M7 的目标里已经有 “permission policy resolves allow/ask/deny” 和 “audit log records every tool execution with policy decision”。 建议把它升级成可 replay 的 event sourcing。

### 12. 明确 M9 前的 readiness gate

你的 milestones 里 M9 是第一次真实 Kaggle end-to-end regression：Spaceship Titanic，目标是通过审批 gate 执行一次真实 `kaggle competitions submit` 并记录 public LB score。 所以 M9 前一定要 gate：

```text
- CI green
- dry-run path green
- Kaggle credentials verified without printing
- submission.csv schema validated
- approval gate manually tested
- rollback / stop criteria documented
- logs/evidence path confirmed
```

## 总结建议

你现在的方向是对的，但下一步要把“经验性流程”固化成产品机制：

```text
Claude Code 开发侧：
  hooks + session closeout + GitHub Actions/Routines/Channels + agents/skills

KCA runtime 侧：
  event log + model router + GitHub adapter + approval gate + replay + evidence bundle

共同核心：
  GitHub repo 是 source of truth
  raw logs 不等于 memory
  human-confirmed decisions 才进入 PROJECT_STATE / ADR / milestones
```

最优先做的不是 M9 继续堆功能，而是 **M8.6：session memory、GitHub event interface、legacy design archaeology、agent/skill reuse packaging**。这会直接提高后续 M9/M10 的开发效率和准确率。
