## 1. Claude Agent SDK 本身免费吗？后端只能接 Anthropic 模型吗？

**SDK 包本身不是单独收费产品，但运行会消耗 Claude/Anthropic 用量。** 官方 Agent SDK 文档显示安装方式是 `pip install claude-agent-sdk` 或 `npm install @anthropic-ai/claude-agent-sdk`，然后通过 `ANTHROPIC_API_KEY` 调用；SDK 提供 Claude Code 同款 tools、agent loop、context management，用于 Python/TypeScript 应用。([Claude Code][1])

计费上有两条路径：

| 使用方式                                          | 计费方式                                                                                                                                                                                                                                  |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 用 Claude Platform API key                     | 按 API token / pay-as-you-go                                                                                                                                                                                                           |
| 用 Claude subscription plan 的 Agent SDK credit | 从 2026-06-15 起，Pro/Max/Team/Enterprise 可领取单独 monthly Agent SDK credit；Pro $20、Max 5x $100、Max 20x $200、Team Standard $20、Team Premium $100 等，超出后走 usage credits/API rate，API key 用户没有这笔 subscription credit。([Claude Help Center][2]) |

后端模型方面，**Claude Agent SDK 官方路径主要是 Claude/Anthropic 模型生态**。它支持 Anthropic API key，也支持通过 Amazon Bedrock、Claude Platform on AWS、Google Vertex AI、Microsoft Azure AI Foundry 等第三方云 provider 认证，但这些仍然是 Claude 模型供应链，不是直接接 OpenAI/Ollama/vLLM。官方 quickstart 明确要求 Anthropic account/API key，并列出 Bedrock/Vertex/Azure Foundry 等 Claude provider 认证变量。([Claude Code][3])

所以结论是：

```text
Claude Agent SDK:
  官方强项 = Claude Code-style agent loop + Claude models + tools/permissions/hooks/session

KCA runtime:
  可以把 Claude Agent SDK 作为一个 backend
  但不要把整个产品锁死在它上面

KCA model router:
  继续保留 LiteLLM / OpenAI-compatible / local vLLM / Ollama 路线
```

也就是说，KCA 未来应该是：

```text
KCA Worker
  ├── Claude Agent SDK backend     # 强 coding / agentic loop
  ├── LiteLLM backend              # Claude/GPT/local统一 completion/router
  ├── OpenAI/Codex backend         # reviewer / alternate solver
  └── local vLLM/Ollama backend    # cheap triage / summarization / batch ideas
```

## 3. Claude Code 使用 machine user 进行 GitHub 操作的好处和设置步骤

你现在本地 Claude Code 如果用你的 `gh` / git 凭据，PR、comments、labels、branches 都会显示成你的用户。这在早期可以接受，但现在你要把 GitHub issues/PR/comments/labels 作为 human ↔ AI 的协作接口，**最好切换到 machine user 或 GitHub App**。

GitHub 官方文档明确建议 unattended/shared bot/service account 要启用 2FA，并用受控邮件列表和集中保存的 TOTP secret 管理共享访问。([GitHub Docs][6]) GitHub 也说明 PAT 是代表某个用户访问 GitHub，长期组织级集成更推荐 GitHub App；若使用 fine-grained PAT，应限制到单个 repo、最小权限、到期时间。([GitHub Docs][7])

### 好处

| 好处                   | 说明                                                                              |
| -------------------- | ------------------------------------------------------------------------------- |
| 审计清晰                 | PR/comment/label 由 `kca-agent-bot` 发出，不和你的 human decision 混在一起                  |
| 权限最小化                | bot 只给目标 repo 的 contents/issues/pull-requests 权限                                |
| 可撤销                  | 出问题直接 revoke bot PAT / remove collaborator                                      |
| 分离职责                 | human 负责 `decision:confirmed`、merge、release readiness；agent 负责实现/triage/comment |
| 便于 branch protection | main 禁 direct push，bot 只能开 branch/PR                                            |
| 支持状态机                | bot 可以自动加 `ai:triage`/`ai:blocked`，但不能自己赋予 human approval                       |

### 推荐设置步骤

**A. 创建 machine user**

1. 创建 GitHub 用户，例如 `kca-agent-bot`。
2. 使用邮件 alias，例如 `kca-agent-bot@yourdomain.com`。
3. 开启 2FA。
4. 把 TOTP secret 放到你的 password manager。
5. 不要把 bot 密码给 Claude；Claude 只使用 SSH key 或 token。

**B. 加入 repo/org**

1. 如果 repo 在 org 下，创建 team：`kca-agents`。
2. 把 `kca-agent-bot` 加入 team。
3. 只给目标 repo `Write` 权限，不给 admin。
4. main branch protection 保持：禁止 direct push、required CI、PR review required、no force push。

**C. 本地 Arch runner SSH 配置**

```bash
# 切到你的 Arch runner
ssh-keygen -t ed25519 -C "kca-agent-bot@yourdomain.com" -f ~/.ssh/kca_agent_bot_ed25519

cat ~/.ssh/kca_agent_bot_ed25519.pub
# 到 kca-agent-bot GitHub account -> Settings -> SSH and GPG keys -> New SSH key
```

`~/.ssh/config`：

```sshconfig
Host github-kca-bot
  HostName github.com
  User git
  IdentityFile ~/.ssh/kca_agent_bot_ed25519
  IdentitiesOnly yes
```

repo remote：

```bash
git remote set-url origin git@github-kca-bot:OWNER/REPO.git
```

git identity：

```bash
git config user.name "kca-agent-bot"
git config user.email "kca-agent-bot@users.noreply.github.com"
```

**D. GitHub CLI token**

生成 fine-grained PAT，repo 只选当前 KCA repo，权限建议：

```text
Contents: read/write
Pull requests: read/write
Issues: read/write
Actions: read
Metadata: read
```

如要同步 labels：

```text
Issues: read/write
```

如要更新 workflow 文件，需要额外谨慎，因为 `workflows` 权限很敏感；通常不要给本地 bot 常开 workflow write。

登录：

```bash
gh auth logout
gh auth login --hostname github.com --git-protocol ssh --with-token < token.txt
gh auth status
gh repo view OWNER/REPO
```

**E. Claude Code permission/hook 策略**

不要再 deny 整个 `~/.ssh/**`，否则 git/ssh 可能不可用；但要继续 block 读取私钥内容。你现在的 `guard_tool.py` 已经会拦截 `cat/less/head/tail/grep` 读取 `.env`、`kaggle.json`、`id_rsa`、`id_ed25519`、`.aws`、`.ssh`，并对 `git push`、`gh pr create/merge` 返回 ask。 这条方向是对的。

建议 M9.6 让 Claude Code 做：

```text
- 从 sandbox denyRead/denyWrite 中移除 ~/.ssh
- 保留或增强 guard_tool.py 对 id_rsa/id_ed25519/.ssh 的 shell-read deny
- git push / gh pr create / gh pr merge 仍 ask
- gh issue edit/comment / gh label create/edit 也 ask 或 policy-gated
```

## 4. 为什么 PR #20 里你后来编辑 comment 加 `@claude` 没有回复？

最可能原因有三个，**第一个最关键**。

### 原因 1：你的 workflow 只监听 `created` / `submitted`，不监听 `edited`

你上传的 `.github/workflows/claude.yml` 目前是：

```yaml
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
  issues:
    types: [opened, assigned]
  pull_request_review:
    types: [submitted]
```

并且 job 的 `if` 只检查这些 event payload 里是否包含 `@claude`。

所以如果你是：

```text
先发 comment
再编辑 comment 加 @claude
```

那不会触发，因为 `issue_comment.edited` / `pull_request_review_comment.edited` 没有在 `types` 里。你需要新发一条包含 `@claude` 的 comment，或者把 workflow 改成监听 `edited`。

### 原因 2：workflow 权限目前是 read-only，无法正常回复/改 PR/开分支

你当前 `claude.yml` 的 permissions 是：

```yaml
contents: read
pull-requests: read
issues: read
id-token: write
actions: read
```

这允许读 repo/PR/issue/CI，但不适合评论、更新 labels、开 branch、创建 PR。 官方 Claude Code GitHub Actions 文档说，Claude Code GitHub Actions 可以通过 PR/issue 里的 `@claude` 触发来分析代码、创建 PR、实现功能、修 bug；quick setup 需要 GitHub App 拥有 Contents、Issues、Pull requests 的 read/write 权限。([Claude Code][8])

### 原因 3：不缺 Channels，也不一定缺 agents/skills

**方案 A GitHub Actions 不需要 Channels。** Channels 是把 webhook 推进一个正在运行的本地 session；GitHub Actions 是每次事件启动一次 action/session。官方 Channels 文档说它用于把 messages/alerts/webhooks 通过 MCP server 推进正在运行的 Claude Code session，且是 research preview，需要 session 正在 open。([Claude Code][9])

因此，PR #20 没回复大概率不是因为缺 Channels 或 skills，而是 workflow event types/permissions/secret/action run 条件问题。agents/skills 是为了让回复更高质量、更符合你的工程流程，不是触发的必要条件。

## 5. 方案 A：GitHub comments/reviews/labels 触发新的后台 session，该怎么设置？

我建议 **以 GitHub Actions 为主，不用 polling**：

```text
issue/pr comment with @claude
  → GitHub Actions event
  → anthropics/claude-code-action
  → 新的 cloud/GHA agent session
  → 读 CLAUDE.md / AGENTS.md / docs
  → 根据 comment 执行 triage / review / implement / fix
  → comment / branch / PR / labels
```

这就是你说的“human submit PR reviews, update comments, add comments to issue or update labels 后，让 Claude Code 在单独 background agent session 中回应”。

### 推荐 workflow 拆分

| Workflow                          | 触发                                               | 权限                                                | 目的                        |
| --------------------------------- | ------------------------------------------------ | ------------------------------------------------- | ------------------------- |
| `claude.yml`                      | `@claude` comment/review/issue，包括 created/edited | contents/write, issues/write, pull-requests/write | 手动调用 Claude               |
| `claude-code-review.yml`          | PR opened/synchronize/ready_for_review           | pull-requests/write 或 read+comment                | 自动 review PR              |
| `issue-triage.yml`                | issue opened/edited/labeled/commented            | issues/write, contents/read                       | label 状态机、提取决策            |
| `labels-state-check.yml`          | issues labeled/unlabeled, PR labeled/unlabeled   | issues/write 或 read                               | 防止非法 label 组合             |
| `pr-closeout-check.yml`           | PR opened/edited/synchronize                     | pull-requests/read                                | 检查 PR body/evidence/tests |
| `github-event-channel-bridge.yml` | 可选：workflow_dispatch / selected events           | issues/read/actions/read                          | 给本地 Channels server 发事件   |

工程实践文档也已经建议这些 workflow：`issue-triage.yml` 用 `issues: write`，`labels-sync.yml` 用 `issues: write`，`pr-closeout-check.yml` 用 `pull-requests: read`，以及 `/loop` 只适合有界地重查 CI/PR comments/artifacts。

### `claude.yml` 需要的关键改动

```yaml
on:
  issue_comment:
    types: [created, edited]
  pull_request_review_comment:
    types: [created, edited]
  issues:
    types: [opened, edited, assigned, labeled, unlabeled]
  pull_request_review:
    types: [submitted, edited]
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review, labeled, unlabeled]

permissions:
  contents: write
  pull-requests: write
  issues: write
  actions: read
  id-token: write
```

同时加并发控制，避免一个 PR 里多条 comment 启动多个互相覆盖的 agent：

```yaml
concurrency:
  group: claude-${{ github.event_name }}-${{ github.event.issue.number || github.event.pull_request.number || github.run_id }}
  cancel-in-progress: false
```


## 10. labels 变成状态机

现在 labels 不应该只是分类，而应该控制 agent 能不能动手。

建议状态机：

```text
new issue
  → ai:triage

needs decision
  → type:decision + decision:needed + ai:blocked

human confirmed
  → decision:confirmed
  → ai:ready

agent starts work
  → ai:implementing

blocked
  → ai:blocked

PR opened
  → ai:implementing remains until closeout

merged / closed
  → remove ai:implementing
  → create follow-up issues for unresolved findings
```

非法组合：

```text
ai:ready + ai:blocked
ai:ready + decision:needed
ai:implementing without ai:ready
decision:confirmed + decision:needed
closed issue + ai:implementing
```

自动化规则：

```text
issue-triage.yml:
  可以添加 ai:blocked / decision:needed / type:* / area:*
  不能自行添加 decision:confirmed，除非 human 明确 comment 包含固定 approval phrase

label-state-machine.yml:
  检测非法组合
  自动评论并修复低风险 label
  高风险 label 变更只报告，不自动改
```

```text
- 改代码
- 跑测试
- 开 PR
- 回应 PR review
- 更新 labels/status
- 把有价值的信息沉淀到 memory
```

那现在开发 KCA 本身时就用同样的模式：

```text
GitHub issue/comment/label/review
  → GitHub event adapter
  → decision extractor / issue triage
  → KCA job or Claude Code Action
  → branch/worktree/session
  → PR / comment / label update
  → closeout / evidence / memory promotion
```

短期这由 Claude Code GitHub Actions 和 repo-level agents/skills 实现；长期 KCA 自己实现：

```text
src/integrations/github/
  events.py / events.ts
  comments.py
  labels.py
  pull_requests.py
  memory_extractor.py

src/worker/
  github_job_runner.py
  agent_session_router.py
```

这会让你边开发边验证 KCA 的核心产品假设：**GitHub 可以作为 human/AI 协作面，labels 可以作为状态机，comments 可以作为需求/设计 evidence，PR 可以作为代码交付边界。**
