---

**A — Summary of comparison presented:**

Two approaches compared:

**Approach A (current M3 design):** jobs run as git worktrees inside the platform repo.
Competition code lives in `src/<competition>/` of the platform repo.

**Approach B (user's original idea):** each competition gets its own GitHub repo
(e.g., `harry/kaggle-flower-tpu-2026`). Branches track experiments:
`main` (baseline), `exp/b0-baseline`, `exp/b3-mixup`, etc.
Agent jobs use git worktrees *within* the competition repo.

Key comparison points raised:
- Approach A mixes platform code and competition code in the same repo — wrong separation of concerns.
- Approach B maps naturally to the Kaggle mental model (one competition = one workspace).
- Branch-per-experiment in a competition repo makes git log a readable experiment history.
- Data, runs/, and artifacts/ are gitignored in the competition repo, cleanly isolated.
- Kaggle kernel metadata naturally points to the competition repo.
- Competitions can be archived or made public independently.
- Worktree and separate-repo solve different levels of isolation: worktree = job-level,
  separate repo = competition-level. The two can be layered.

Recommended layering:
```
Competition repo (harry/kaggle-flower-tpu-2026)
  branch: main             ← clean baseline
  branch: exp/b3-mixup     ← experiment branch

Worker runtime:
  git clone → .competition-workspaces/flower-tpu/
  git worktree add jobs/<job_id> exp/b3-mixup
  agent runs inside worktree
  on completion: merge/PR back to branch
```

Transition plan offered: use platform repo worktree in M3 (simpler, gets worker skeleton
working), migrate to competition repo strategy in M4 (Kaggle workflow v0).
